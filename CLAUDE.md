# Project context for Claude Code

## What this is

`agx` is a host-side Python CLI that manages AI agents (Hermes Agent from Nous Research, OpenClaw) inside a single Multipass VM with rootless Docker. The host invokes only `multipass` — it never talks to the in-VM Docker daemon directly. Outer trust boundary = VM. Inner trust boundary = one Docker container per agent. The defense-in-depth motivation is the 2026 wave of agent-marketplace malware and skill-execution CVEs.

## Locked architecture rules (do not relitigate)

0. **VM backend is pluggable.** `cfg.vm.backend` selects `multipass` (cross-platform default), `libvirt` (Linux-only, experimental — enables GPU passthrough; see GH #2), or `bare_metal` (Linux-only, no VM at all — see GH #5). `mp.py` is a dispatcher; the real implementations live in `agx_cli/backends/{multipass,libvirt,bare_metal}.py`. Backend modules are duck-typed (free functions matching `VmBackend` Protocol). `cli.main` calls `mp.set_backend(get_backend_module(cfg.vm.backend))` once at startup; everything else uses `mp.foo(...)` and stays backend-agnostic. **Never add new VM-host primitives directly to `mp.py`** — add them to ALL THREE backend modules + the dispatcher in `mp.py`.
1. **Rootless Docker inside the VM.** Daemon runs as `ubuntu`, socket at `<docker_socket_path>` (read from `[vm_runtime]` in config — set by BOOTSTRAP_OK). Never hardcode the path or the UID.
2. **One mount, one source of truth.** Host `<data-dir>` is mounted at VM `/home/ubuntu/agents` with explicit `multipass mount -u <host-uid>:1000 -g <host-gid>:1000`. All per-agent data, the compose file, the `.env`, exports, and the toolkit-scoped Codex auth live under this path. The VM disk only holds OS + Docker engine + image cache. Opt-out is `vm init --data-dir-in-vm` — **recommended for SQLite-heavy workloads** (Hermes' kanban/sessions/insights stores use WAL, which doesn't work over the 9p share; in-VM ext4 fixes that). Under `--data-dir-in-vm` agent state is host-visible only via `agx export` archives; `agx export-cron install --time 02:30,08:30,14:30,20:30` gives you 6-hourly archives that duplicity picks up natively.
3. **Toolkit-scoped Codex auth** at `<data-dir>/.codex/` — NEVER the user's personal `~/.codex/`. `agx codex login` sets `CODEX_HOME=<data-dir>/.codex`. It feeds ONLY the Codex *sandbox skill* (`/codex:ro` in the derived sandbox image). It is NOT how a Hermes agent's `openai-codex` LLM provider authenticates — that is `agx exec <name> -- hermes auth add openai-codex --type oauth --no-browser` inside the container (see the Codex-lineage pitfall below). `agx codex refresh` is retired (hidden stub).
4. **The CLI owns the compose file.** Users get `docker-compose.override.yml` for hand edits. Never heredoc through `multipass exec` — always: flock → ruamel.yaml round-trip → write host temp via `compose.host_staging_dir(cfg)` (= `<host_data_dir>/.staging/`) → `multipass transfer` to `<vm_agents_root>/.compose.<pid>.<uuid>.new` → `docker compose --project-directory <vm_agents_root> -f ... --env-file <vm_agents_root>/.env config -q` validation → VM-side `mv` to `docker-compose.yml` (atomic same-fs rename) → cleanup. Host staging path is NOT under `/tmp/` (snap-confined `multipass` — the default Ubuntu install — cannot SFTP from `/tmp`: `cannot access`) and NOT under `$HOME/.cache/` (snap's home interface excludes dotfile paths: `Permission denied`). Staging under the host data dir works because that dir is already `multipass mount`ed into the VM, so multipass has explicit access — guaranteed on both snap and deb installs. Every module that `multipass transfer`s a host file into the VM (`compose`, `hermes_config`, `codex` for Dockerfile + auth-tar sync) uses `compose.host_staging_dir(cfg)` — do NOT introduce new `/tmp` or `~/.cache` paths. `compose.cleanup_stale_temps(cfg)` is invoked by `vm.start` and at the head of every mutation. Same pattern applies to per-agent `config.yaml` writes via `hermes_config.write_atomically`, which validates via `hermes config validate` exec'd inside the running container (best-effort — silently skipped if the container isn't up yet).
5. **Image-source allowlist** is a parsed `(registry, repo)` tuple match — `nousresearch/hermes-agent`, `openclaw/openclaw`, `volcengine/openviking` (memory sidecar), `ghcr.io/firecrawl/firecrawl` + `ghcr.io/firecrawl/playwright-service` + `ghcr.io/firecrawl/nuq-postgres` (firecrawl stack), and `redis` + `rabbitmq` (firecrawl dependencies). Reject `hermes-agent.org` and any registry-prefixed variant. `validate_image_ref` handles `repo`, `repo:tag`, AND `repo@sha256:…` (digest pin) forms — strips `@sha256:…` BEFORE partitioning on `:`. New sibling-service backends require explicit allowlist additions in `compose.py`.
6. **Dashboard binding** is `127.0.0.1`/`localhost` only. The CLI refuses any Hermes config change to `0.0.0.0`.
7. **Every mutation holds `<data-dir>/.agents.lock`** (`flock`). Read-only commands skip the lock. Two parallel `agx create` calls must serialize.
8. **Every multi-phase op writes a phase journal** at `<data-dir>/.journal/<op>-<name>-<utc>.json`. Re-running the command resumes from the last completed phase. `doctor` flags journals older than 24 h.
9. **Compose service blocks are written once and never auto-regenerated.** When the service-fragment template evolves (new env var, changed volume layout), existing agents keep their stale block forever. `agx reseat <name>` is the explicit "rewrite this agent's compose service entry from the current fragment, preserving port + image tag + env_file additions + depends_on additions, then force-recreate" command. Run after toolkit upgrades.
10. **`docker-compose.override.yml` is sacred** — the toolkit appends to it (currently only via `agx mount`) but never rewrites it from a template, never deletes user keys, never runs it through reseat. Both layers — `docker-compose.yml` (toolkit-owned, full rewrites allowed) and `docker-compose.override.yml` (additive only) — exist precisely so user-and-`agx mount` additions survive every `agx reseat` / `agx upgrade`. New features that need to add per-agent runtime knobs (e.g. extra volumes, extra env, extra ports) go in the override file via `compose.read_override_doc` / `compose.write_override_atomically`, not the primary compose. Mutations must hold `<data-dir>/.agents.lock` like every other compose write.

## Critical cross-layer pitfalls (already fixed; don't reintroduce)

- **The CLI was renamed `agents` → `agx` (2026-10); only TOOL identity was renamed, never live-state identity.** Renamed: console script (`agx`; the transitional `agents` alias was removed again on 2026-10-13), package (`agx_cli`, distribution `agx-cli` — PyPI `agx` is AGX Dynamics, also an import-name clash), config dir (`~/.config/agx/`; `config.migrate_legacy_config_dir`, called at the top of `cli.main`, moves the old dir once, never overwriting; installs migrated before 2026-10-13 may still have a `~/.config/agents -> agx` symlink, which it ignores). Deliberately NOT renamed, because they name running infrastructure or persisted state: the VM / libvirt domain / tailscale hostname default `agents`, the data dir and `/home/ubuntu/agents`, `.agents.lock`, journal names, crontab markers (`# agents toolkit — managed …`; lines installed before the rename still call `agents` and FAIL until `export-cron`/`doctor-cron install` rewrites them to `agx`), `AGENTS_BARE_METAL` (set alongside `AGX_BARE_METAL`). Unit tests must not migrate the developer's real config: `tests/conftest.py` repoints `config.LEGACY_CONFIG_PATH`, and the migration reads module globals at call time for that reason.

- **Snap-Multipass + libvirt on the same host fight over `/dev/kvm` group ownership.** `/etc/udev/rules.d/70-snap.multipass.rules` tags `/dev/kvm` with `snap_multipass_multipassd`, which causes `snap-device-helper` to reassign the device's group to snapd's sandboxed namespace (typically `systemd-resolve`). libvirt-qemu (group `kvm`) then can't open `/dev/kvm` and every libvirt VM start fails with "Could not access KVM kernel module: Permission denied". Fix is to drop `/etc/udev/rules.d/99-fix-kvm-group.rules` with a `RUN+=` that re-asserts `chgrp kvm /dev/kvm` AFTER snap's rule (99- sorts after 70-). Documented in `docs/runbook.md#using-the-libvirt-backend`.
- **libvirt + virtiofs requires `<memoryBacking><source type='memfd'/><access mode='shared'/></memoryBacking>` in the domain XML.** Without it, `virsh attach-device` of a `<filesystem type='virtiofs'>` block succeeds but the guest mount hits "Transport endpoint is not connected". The toolkit emits `--memorybacking source.type=memfd,access.mode=shared` on every `virt-install`; never hand-edit the launch path to drop it.
- **Host writes reach the VM late over the shared folder — wait before a VM-side `docker compose` reads them.** virtiofs (libvirt, default cache) kept serving the OLD content for ~0.5-1 s after a host-side rename (measured 2026-10-12): `agx mount remove --restart` wrote the override, `compose up` read the stale copy, saw no change ("Running"), and the container kept the removed bind mount. `compose.await_vm_view(cfg, host_path)` polls `sha256sum` in the VM until it matches (≤ 5 s, warns instead of raising; no-op on bare-metal and `--data-dir-in-vm`). Called by `write_override_atomically`, `ensure_cont_init_script`, `secrets_cmd._write_env`, `sidecar.write_project_env` and create's empty `.env`. Any NEW host-side write that a VM-side compose/container start consumes must call it too (VM-side `mv` writes, like the main compose's, don't need it). Unit tests no-op it via an autouse fixture (`compose._await_vm_view_impl` is the real one).
- **libvirt `agx mount` was broken end-to-end until 2026-10-12 (Phase-B "untested" code).** (1) QEMU caps a virtiofs tag at 36 bytes; the tag was the whole VM path (`home_ubuntu_host-extras_<agent>_<sha8>-<base>`), so every `mount add` failed — `backends/libvirt._virtiofs_tag` keeps the legacy form when it fits (the data-dir share `home_ubuntu_agents` is attached on live VMs) and hashes otherwise. (2) `virsh detach-device` matches virtiofs devices on their `<source>` too ("missing source information"), so every `umount` failed and `mount remove` silently leaked the share — `umount` now detaches the exact element from `dumpxml --inactive` (`_filesystem_element_for_tag`), removes the empty mountpoint, and `mounts_cmd.remove` warns when the detach fails.
- **libvirt + virtiofs cannot snapshot a running VM** — vhost-user backend lacks `VHOST_USER_PROTOCOL_F_LOG_SHMFD`. `vm.take_snapshot` / `vm.restore_snapshot` detect the case (backend=libvirt AND not data-dir-in-vm) and run a confirmed stop → snapshot → start cycle. Why not detach-virtiofs-snapshot-reattach: live `umount` is refused while Docker containers have bind mounts underneath; `umount -l` works but leaves containers with stale FDs (SQLite-WAL corruption risk for state.db / kanban.db). Full-VM-stop matches container lifecycle and is what `agx vm stop` already does cleanly.
- **libvirt VM init must be transactional** — `virt-install` can leave a defined-but-unstartable domain if e.g. `wait_for_ssh` times out after the domain is registered. `vm.init`'s libvirt branch wraps launch + wait + GPU-attach in try/except and calls `libvirt._cleanup_partial_domain` on failure (destroy + snapshot-delete --metadata + undefine --remove-all-storage). Without this, retry would be blocked by the orphan domain.
- **AMD systems often ship with `amd_iommu=off` in the kernel cmdline** (Strix Halo / Ryzen AI MAX, several Ryzen laptops). It's a leftover BIOS-stability workaround from early 2025. GPU passthrough is impossible until the user updates BIOS + flips to `amd_iommu=on iommu=pt`. The toolkit doesn't try to detect or fix this (host-level + reboot); doctor checks just surface `iommu_group=""` for affected GPUs.
- **Rootless-Docker subuid mapping is why agent files look "foreign" on the host — and it cannot be fixed at the source.** Container uid 1000 (the hermes/openclaw runtime user) maps to `<subuid_base> + 999` (typically 100999); the agent's state dir is owned by that with mode 700. The userns map is bijective and the host user's uid is already taken by *container root*, the Hermes image refuses `HERMES_UID=0` and `--user`, virtiofsd < 1.13 has no `--translate-uid`, and the VM kernel (6.8) has no virtiofs idmapped mounts (9p never will) — so don't relitigate "just make the files host-owned". **Don't** chown inside the container either (the entrypoint reverses it). Human access is an *idmapped bind-mount view on the host*: `agx access mount <name>` mounts `<name>/.data` at `<view-root>/<name>` (`[paths].host_view_dir`, default `~/agents-view`) with host-uid ↔ on-disk-uid swapped, so through the view the host user IS the owner and mode bits / chmod / ACL masks are irrelevant. Load-bearing details: ids come from `os.stat` of the source, NOT `/etc/subuid` math (the host's file only matches the VM daemon's mapping by coincidence — `permissions.compute_container_subuid` is for `agx mount add` only); the spec is swap + identity ranges tiling the whole id space (unmapped ids show as `nobody`; overlapping extents are rejected by the kernel — hence host-owned targets like OpenClaw's `workspace` are skipped); options are always `nosymfollow,nosuid,nodev,noexec` and `ro` unless `--rw`, because the view carries agent-written (untrusted) content into the HOST namespace — a planted `SOUL.md -> ~/.bashrc` must not resolve there; mount state is read from `/proc/self/mountinfo` via `idmap_view` because `os.path.ismount` cannot see a same-filesystem bind mount (it would stack mounts and warn forever), and the expected `root` field is derived from the containing mount (it's only the absolute path when the data dir is on `/`); `unmount` is `umount` + plain `rmdir`, NEVER a recursive delete of a view path (same `st_dev` as the data — that would delete the agent's state); the toolkit prints a `nofail` fstab line and never edits `/etc`; registered views live in `<data-dir>/.access-views.json` (opt-in gate for doctor's `host_view` check), and `remove`/`rename`/`vm migrate-data` refuse while one is registered. Works on bare_metal too; refused under `--data-dir-in-vm`. `agx edit` is the zero-mount, zero-sudo path for single files. `agx mount add` still auto-applies ACLs on *user-owned host folders* via `permissions.py` — that's the only remaining ACL use.
- **Why ACLs were retired for agent data dirs (2026-09): chmod clobbers the ACL *mask*, and restrictive creates are BORN masked.** The toolkit used to grant the host user a default ACL at `agx create` plus a sudo `agx access grant`. The Hermes entrypoint chmods subuid-owned paths (`.data` → 700, auth files → 600), which resets each object's POSIX-ACL mask to `---`: the host-user entry stays present but reads `#effective:---`. Worse (reproduced 2026-09): a `mkdir(0700)` / `open(0600)` under a default ACL gets `mask::---` at creation, so every private dir Hermes makes at runtime is unreadable from day one — no boot-time heal can keep up. Bit us live 2026-07: `agx remove` died with `PermissionError: '.data'`. **Rule: host-side toolkit code never traverses runtime-owned agent state (`.data`, `.openclaw`, `workspace`). Go through root in the VM (`sudo` via `mp.exec_*` — guest root acts as root on the share) or `docker compose exec` as the runtime user.** Already converted: `remove` (`agents_cmd._delete_data_dir` → VM-side `sudo rm -rf` behind a share-mounted check + a no-mounts-beneath check, since `--one-file-system` does NOT stop same-fs bind mounts; host-side postcondition), `export`/`import`, upgrade snapshot + rollback restore (`sudo tar` in the VM, BOTH data-dir modes — the `--data-dir-in-vm` branches used to run an unprivileged tar with `--ignore-failed-read`, i.e. hollow archives), `hermes_config`, `agx edit`. Toolkit metadata under the agent dir (`<name>/.env`, `.mounts.json`) is host-owned and stays host-managed. `remove` still consults `Journal.find_resumable` before raising "not found in compose" (recovering `agent_type` from journal meta), and `create` refuses while a remove journal for the name is pending. **bare_metal is NOT an exception:** it runs rootless Docker too, so agent files are subuid-owned there as well (older comments claiming a 1:1 uid mapping are wrong); its delete path is `rootlesskit rm -rf` (userns root owns the subuid range on a local fs) with confirmed sudo as fallback.
- **`--backend bare_metal` forfeits the VM trust boundary** — the host becomes the boundary. A compromised agent that escapes its container reaches the host directly. The defense-in-depth motivation in this file still applies for most users; bare-metal is opt-in for single-user dev workstations / dedicated LLM boxes only. The init flow warns the user explicitly. Three concrete behavior differences from VM-mode that are easy to miss: (a) bootstrap is **verify-only** — `bare_metal.verify_bootstrap` probes rootless-Docker prerequisites and refuses with hints (`sudo apt install ...`, `curl ... | sh`, `loginctl enable-linger`) rather than running sudo on the user's behalf; (b) `vm.init` sets `cfg.paths.vm_agents_root = cfg.paths.host_data_dir` so `compose_runner._base_argv` produces correct host paths unchanged — any new code that interpolates `vm_agents_root` for an SSH/multipass-exec context must NOT assume it differs from `host_data_dir`; (c) snapshots are refused (no VM disk to snapshot — use `agx export` + host-level duplicity/restic); (d) every `docker` call is pinned to the recorded rootless socket — `bare_metal._docker_env` forces `DOCKER_HOST` and drops `DOCKER_CONTEXT` (`cli.main` calls `bare_metal.configure(cfg.vm_runtime.docker_socket_path)`), because on the host the ambient env/context (a shell rc, cron's minimal env, a rootful daemon the user also runs) would otherwise pick the daemon; (e) there is no `host-extras` VM mount, so `agx mount` binds the host folder itself (`MountEntry.volume_source`) and still applies the subuid ACLs — before 2026-10 it wrote the non-existent VM path as bind source and skipped the ACLs on the false "uid maps 1:1" premise. When adding a new feature, gate VM-specific code paths on `cfg.vm.backend in ("multipass", "libvirt")` rather than enumerating bare-metal exclusions, so future backends don't silently break.
- **`terminal.docker_volumes` paths are interpreted by the VM Docker daemon**, not by paths inside the Hermes container. Sandbox volume entries use VM-side host paths like `/home/ubuntu/agents/.codex:/<sandbox-user>/.codex:ro`.
- **Hermes runtime container needs `DOCKER_HOST` env** plus the rootless socket mount, otherwise its CLI can't reach the daemon to spawn the sandbox.
- **Multipass snapshots do NOT cover the host-mounted data-dir.** Upgrade flow takes BOTH a VM snapshot AND a host-data tarball (in `<data-dir>/.upgrades/`).
- **Rootless Docker ships NO container-log rotation** — the json-file driver grows unbounded, and one chatty container can take the VM disk down alone (firecrawl-postgres: 2.8 GB in 5 days; a transient disk-full at 2026-08-24 00:30 ENOSPC'd rabbitmq mid-write, wedging it in `health: starting` and killing web search for every wired agent, since a stopped `firecrawl-api` also drops its Docker-DNS name → agents see "could not resolve host", not a connection error). The bootstrap now writes `~/.config/docker/daemon.json` with `log-opts: max-size=50m, max-file=3` BEFORE the daemon's first start (step 3b2; never clobbers an existing file). Caveat: log-opts apply per-container at CREATE time — containers created before the option keep unbounded logs until their next recreate (reseat/upgrade/firecrawl `up --upgrade`). **bare_metal has no such bootstrap step** (verify-only — it must not rewrite the user's daemon config, and there the disk that fills is the HOST root fs): `vm init` warns via `vm._warn_bare_metal_log_rotation`, and doctor's `container_logs` check (`ops._check_container_logs`, every backend) is the standing guard — it parses the daemon's `daemon.json` (`ops.daemon_log_rotation_gap`) AND inspects the compose project's containers (filtered by the `com.docker.compose.project.working_dir` label) for json-file logs without `max-size`, naming the ones that need a recreate.
- **Upgrade artifacts used to accumulate unboundedly and filled the VM disk to 100% (2026-08 outage).** Each `agx upgrade` leaves a superseded image tag (~4-9 GB for Hermes) in the VM's Docker cache plus a VM snapshot and a host tarball; eight releases of routine upgrades exhausted a 58 GB VM disk, and the symptom was obscure — Hermes' gateway answered "session storage could not be written" because the container's overlay fs (VM root disk) had 0 bytes free while `/opt/data` (host mount) had plenty. Two guards now exist and must both survive refactors: doctor's `vm_disk` check (`df -Pk /` in the VM — the host-side `disk_space` check can't see the VM disk) and the post-upgrade auto-prune (`prune_cmd.auto_prune_after_upgrade`, keeping `[upgrades].keep_generations` generations). Retention is generation-counted, NOT age-based: `agx rollback` only uses the newest generation, and age-based expiry could delete the only rollback point of a rarely-upgraded agent.
- **Under `--data-dir-in-vm` the override file has TWO copies and the host one is authoritative.** `compose.override_file_args` arms the extra `-f` from the HOST copy; `write_override_atomically` mirrors it into the VM project dir. `vm rebuild` destroys the mirror with the VM disk while the host copy survives, so every compose verb in the fresh VM failed on a missing file (stranded `agx mount` users, found 2026-09). `compose.sync_override_to_vm` re-pushes the raw host file: called by the in-VM seeding (`vm init`, hence `rebuild`) and, `only_if_missing`, by `vm start`; doctor's `override_mirror` check flags the gap. Any new code that creates/replaces the VM project dir in that mode must call it.
- **Multipass mount does not always survive stop/start.** `agx vm start` verifies and remounts, then runs a write/read/unlink probe.
- **Multipass mount MUST be `--type native`, not the default `classic` / fuse.sshfs.** Rootless Docker cannot bind-mount paths from a fuse.sshfs filesystem into a container — kernel returns `operation not supported` and every agent fails on first start. Native uses 9p (Linux/QEMU) or virtiofs (macOS/HyperKit), which Docker handles fine. Native mounts require the VM stopped to add, so `vm._ensure_mount` does a stop→mount→start dance when needed; mounts persist across reboots so it's a one-time cost.
- **No `user:` override on Hermes container under rootless Docker.** Container UID 0 maps to the rootless host user (`ubuntu`/1000) which owns the multipass-mounted data dir. Setting `user: 1000:1000` would push the process into the rootless subuid range (e.g. host uid 100999) and every write into `/opt/data` would be permission-denied. The fragment pins HOME and PATH to the image's OWN values (see the self-modification pitfall) because `docker exec` bypasses the entrypoint.
- **Compose env must pin PATH — to the image's own `Config.Env` value** (`compose.HERMES_PATH`: `/opt/hermes/bin:/opt/hermes/.venv/bin:/opt/data/.local/bin:…`). Old images only got the venv onto PATH via the entrypoint, which `docker exec` (`agx doctor` → `hermes doctor`) bypasses → `executable file not found`. The pin used to omit `/opt/hermes/bin`, silently bypassing upstream's `hermes` wrapper; keep it in sync with `docker image inspect --format '{{json .Config.Env}}'` when Hermes changes it.
- **Rootless Docker install does NOT ship the compose plugin.** `get.docker.com/rootless` installs only daemon + CLI. The bootstrap adds Docker Inc's apt source and installs `docker-compose-plugin` system-wide (lands at `/usr/libexec/docker/cli-plugins/`, picked up by the rootless CLI via plugin auto-discovery).
- **`/home/ubuntu/bin` MUST be on the system PATH** (`/etc/environment`). The rootless install puts `docker` there; `multipass exec` doesn't source `.profile` so without this the toolkit hits `bash: docker: command not found`. The bootstrap prepends it idempotently.
- **OpenClaw service paths are per-agent** (`compose.OPENCLAW_STATE_MOUNTS`: `./<name>/{.openclaw,workspace,.config,.local}`) so multiple named OpenClaw agents don't collide.
- **The OpenClaw image runs as non-root `node` (uid 1000) — it could write NOTHING to toolkit-created dirs until 2026-10.** Under rootless Docker the host user is container ROOT and `node` is a subuid, so `./<name>/.openclaw` created host-side gives `Permission denied` on OpenClaw's own state dir (reproduced with `openclaw/openclaw:2026.10.1`; no OpenClaw agent had been run end-to-end before). `agents_cmd.prepare_openclaw_state` creates the dirs and `chown -R 1000:1000`s them via `compose_runner.run_as_root` (a one-off `compose run --user 0`, i.e. userns root — the host user can't chown into the subuid range) before the first `up`, at create AND reseat. Any new OpenClaw mount needs to go through it. Don't bind-mount over all of `/home/node`: the image ships files there (`.local/share/pnpm`, `.config/openclaw`) that an empty bind source would hide — upstream's `OPENCLAW_HOME_VOLUME` works only because a NAMED volume is pre-seeded from the image. OpenClaw 2.0 (`v2026.8.1`) facts that shaped this: official compose adds `/home/node/.config/openclaw` (auth-profile secret key — was on the overlay, lost per recreate); the image entrypoint runs `openclaw doctor --fix --non-interactive` on every image change (sessions → SQLite, ONE-WAY — downgrading needs manual conversion; exit 78 when it can't migrate safely), so `agx upgrade`'s pre-start data tarball is what makes rollback possible; provider id `openai-codex`/`codex/*` became `openai/*` (login: `openclaw models auth login --provider openai --device-code`); OpenClaw handles SQLite on 9p/virtiofs itself (rollback journaling); the gateway binds `lan` in Docker by default, so the `127.0.0.1:<port>:18789` publish works.
- **GitHub release tag ≠ Docker image tag, per upstream.** Hermes images carry the release tag verbatim (`nousresearch/hermes-agent:v0.21.6`); OpenClaw's drop the `v` (`v2026.10.1` → `openclaw/openclaw:2026.10.1`; `:v2026.10.1` 404s). Until 2026-10 the toolkit pinned the release form for OpenClaw, so `vm init`'s default (`v2026.5.12`) made every `agx create --type openclaw` fail at pull. `outdated_cmd.image_tag_from_release` is the ONE conversion point (also rejects non-version tags like OpenClaw's `linux-stable` channel); `fetch_latest_tag` returns image tags; `normalize_image_tag` repairs user-/config-supplied tags in `create` and `upgrade --tag`. OpenClaw also publishes maintenance releases of older lines AFTER newer ones (`v2026.6.35` on 2026-09-10, after `v2026.9.x`), so "newest-created release" is not "newest version" — `--include-prerelease` takes the first pre-release or the marked-latest stable, never `data[0]`; and versions are still never compared numerically (Hermes' calver→semver switch). **A release does not even guarantee an image under ANY version tag:** Hermes v0.21.7 (GitHub release 2026-10-12) was published to Docker Hub only as `:stable`/`:latest`/`rc.15-v0.21.7` (its notes point Docker users at `:stable`) — no `:v0.21.7` — so every `create` resolving "latest" failed at pull. `outdated_cmd.image_tag_published` (public Docker Hub tag API from the HOST, works before a VM exists; `None` = inconclusive → proceed) now gates it: `create` falls back to the configured default with a warning, `vm init` to the template fallback, `upgrade --latest` refuses BEFORE any snapshot/stop/pin. `outdated` still reports such a release as `outdated` (it compares release tags). Unit tests stub `_http_status` alongside `_fetch_json` (autouse).
- **Agents modify themselves — every such change must land on a bind mount, and no toolkit path may silently revert one.** Survives everything: Hermes `/opt/data` (incl. `home/` = HOME of Hermes' tool subprocesses, `installs/` = lazily installed SDKs), OpenClaw's four state mounts. Lost on every recreate (upgrade, reseat, fix-perms, secret set, mount --restart, memory, codex skill-*, vm rebuild): the container writable layer. Hence: (1) Hermes' container HOME is pinned to the persisted passwd home `/opt/data` (`compose.HERMES_HOME_DIR`); the old `/home/hermes` pin (overlay) existed only for the retired Codex bridge and dropped whatever `docker exec` processes (`agx exec` sessions, doctor's `hermes doctor`) wrote under `~` — the gateway itself was never affected: the image's s6 startup resets HOME from passwd, so its processes always ran with HOME=/opt/data (verified on coder, 2026-10-12). (2) `agx rollback` exports the state it is about to overwrite to `<data-dir>/backups/pre-rollback/` (`upgrades._save_pre_rollback_state`; ALL agents when a VM-snapshot restore rewinds `--data-dir-in-vm` data) and aborts if that fails — a manual rollback days after an upgrade used to discard every skill/memory/session since, and restore a stale single-use OAuth refresh token. Deliberately NOT under `.upgrades/` (rollback would pick its own safety copy as "latest", prune would count it) and NOT top-level `backups/` (export's rolling prune). (3) Toolkit writes to an agent's `config.yaml` are optimistic-concurrency checked: `hermes_config.read_doc` records a hash, `write_atomically` re-reads right before its rename and raises instead of reverting an edit the agent made in between. New code must read via `read_doc` to get that protection.
- **Codex sandbox image tag** must be slugified (`agents/hermes-sandbox-codex:<sha256(base)[:12]>`) — base refs contain `/` and `:`.
- **Image-baked Hermes paths need runtime-user write — they're lost on every container recreate.** Symptom: `hermes setup` (or any other in-container install) hits `EACCES: permission denied, mkdir '/opt/hermes/scripts/whatsapp-bridge/node_modules'`. Cause: `/opt/hermes/scripts/` and `/home/hermes/` are baked into the image owned by root (or whatever USER the image was built as). The runtime user is `hermes`/1000 after the entrypoint's `usermod`, but `usermod` doesn't migrate the home dir, and image-baked subdirs of `/opt/hermes` stay root-owned. Every recreate (`docker rm -f` + `compose up`) wipes the container's overlay fs, so any chown is ephemeral. Remediation: `fixperms_cmd.chown_hermes_install_paths(cfg, svc, huid)` runs after every recreate — called from `agx create` (service_up phase), `agx fix-perms`, and `agx reseat`. Targets list lives at `fixperms_cmd.HERMES_WRITABLE_PATHS`; each entry pairs a target with a tuple of paths to `-prune` so the recursive chown doesn't follow read-only bind-mounts (historically the Codex import bridge at `/home/hermes/.codex:ro`, retired 2026-09 but still mounted on not-yet-reseated agents). **Any new code path that force-recreates a Hermes container must call this helper after start** or `hermes setup`'s install branches will silently regress. **Durable fix (2026-06):** the toolkit now bind-mounts a managed s6 cont-init.d script (`templates.HERMES_CONT_INIT_FIXPERMS`, materialized by `compose.ensure_cont_init_script` into `<data-dir>/.toolkit/cont-init/99-fixperms`) at `/etc/cont-init.d/99-toolkit-fixperms` in every Hermes container. It re-applies this chown on EVERY boot — restart, upgrade-recreate, host-reboot — not just toolkit-driven recreates, which is what kept re-breaking after `agx upgrade`. New agents get the mount at create; existing agents pick it up via `agx reseat`. The materializer (`ensure_cont_init_script`) runs at create (before the fragment is written), reseat, fix-perms, AND upgrade, before each issues its `compose up`; the file then persists on the project dir so other recreate paths (`secret set`, `memory`, `codex skill-*`, vm rebuild) find it present, and a template bump is re-applied on the next reseat. The explicit `chown_hermes_install_paths` call ALSO runs in `upgrade`'s recreate now (it historically didn't — the root of the treadmill), so even an agent whose fragment predates the hook (not yet reseated) is fixed on upgrade; it stays belt-and-suspenders for reseated agents and the first boot before the mount exists. NOTE: this fixes the *permission* half only — the WhatsApp bridge's `node_modules` still lives on the overlay fs and is wiped on every recreate, and its `@whiskeysockets/baileys` **git** dependency sometimes reinstalls empty (`ERR_MODULE_NOT_FOUND`); the fix there is a clean `npm ci` in `/opt/hermes/scripts/whatsapp-bridge`, a separate concern from perms.
- **`/opt/data` permission drift is a recurring class of bug.** Symptom: `agx exec coder hermes <anything>` hits `PermissionError: '/opt/data/.env'` (or similar). Cause: the Hermes image entrypoint *should* `usermod -u $HERMES_UID hermes` on container start, but sometimes doesn't — `docker compose up -d` skips entrypoint when it thinks there's no drift, and stale containers from before HERMES_UID was wired in keep running with hermes=10000. `/opt/data` ends up owned by uid 10000 mode 700; `agx exec` runs at uid 1000; EACCES. Detection: `_check_hermes_data_dir_accessible` in `ops.py` probes `stat /opt/data` as the runtime uid every doctor run. Remediation: `agx fix-perms <agent>` — force-remove the container, recreate fresh (entrypoint runs), then `chown -R <huid>:<huid> /opt/data` + `chmod 755 /opt/data`. The chmod 755 is a band-aid for when the entrypoint *still* doesn't honour HERMES_UID; mode-600 files (auth.json etc.) stay private. The chown runs against the LIVE container, and Hermes prunes its own state on boot (`collect_generations` deletes superseded `installs/*/environments` venvs, tens of thousands of files), so vanished-mid-walk `No such file or directory` errors are expected: `chown_data_dir` tolerates stderr consisting only of those (`_only_vanished_paths`). Before 2026-10-12 they aborted `reseat`/`fix-perms` after the recreate, skipping the chmod + install-path chown.
- **The s6 supervision tree runs as container-root, but `/opt/data` is a 9p/virtiofs mount that IGNORES the container's root capabilities — only the runtime `hermes` uid can write there.** This is the non-obvious asymmetry behind a class of "agent silently stops replying" bugs. As container-root, `chown`/`mkdir` on the **overlay fs** (e.g. `/opt/hermes/scripts`) WORKS (CAP_CHOWN honored in the userns); the SAME op on the **9p-backed `/opt/data`** FAILS with `Permission denied`, because container-uid-0 maps to the unprivileged host/VM user while the mount is owned by the hermes subuid, and 9p enforces DAC at the VM level where the container's userns caps don't apply. It first bit us on Hermes ≥ v2026.5.29: the image's `gateway-default/log/run` does `mkdir -p /opt/data/logs/gateways/default` **as root**, which fails under rootless Docker, so the gateway log service hot-loops, `hermes gateway` never sustains, and the agent receives/answers nothing (`agx logs <name>` shows `s6-log: fatal: unable to mkdir ...`). The cont-init hook encodes the split-privilege rule: chown the overlay install-paths AS ROOT, but pre-create `/opt/data/logs/gateways/default` via `s6-setuidgid hermes` (called by absolute path `/command/s6-setuidgid`, since the cont-init PATH doesn't include `/command`). The leaf must be pre-created (not just the parent) and owned by hermes so the image's buggy root-`mkdir -p` no-ops and `s6-log` (which runs as hermes) can write. Upstream bug — worth reporting to Nous; worked around toolkit-side meanwhile.
- **`localhost` / `127.0.0.1` / `0.0.0.0` are refused in `[ollama]` URLs** (`OllamaConfig._validate_url`). Inside the VM those resolve to the VM itself, not to the host where the user is actually running Ollama. The toolkit suggests the multipass NAT gateway (`multipass info <vm>` → IPv4) when surfacing the error.
- **Memory backends needing embeddings/LLM read from `[ollama]` only.** The toolkit does NOT manage an Ollama instance. mem0 and OpenViking refuse to install when `[ollama]` is empty (mem0 falls back to `OPENAI_API_KEY` in `.env` if present; OpenViking does not, since its fact-extraction loop would melt a personal ChatGPT subscription).
- **`/home/hermes` must be created explicitly — the image never does, and it used to exist only as a side effect of the retired `.codex` bridge mount.** (Legacy since 2026-10: current fragments pin HOME=/opt/data; the mkdir stays for agents not yet reseated.) `HOME=/home/hermes` was pinned in the Hermes fragment; after the bridge mount was dropped (2026-09-21) the dir stopped appearing, npm had no cache/log dir, and the WhatsApp bridge's `npm ci` failed half-way on every boot (`ERR_MODULE_NOT_FOUND @cacheable/utils`, bridge crash-looping). Both `fixperms_cmd.chown_hermes_install_paths` and the cont-init hook now `mkdir -p /home/hermes` (as root, overlay fs) before the existence-gated chown. Never remove a toolkit mount without checking what parent dirs Docker was implicitly creating for it.
- **`hermes doctor`'s exit code is not a health verdict — and Hermes changed it under us (v0.21.6, 2026-10-08).** ≤ v2026.9.x exited 0 even with `✗` findings; ≥ v0.21.6 exits 1 whenever it reports ANY issue, including advisory `⚠` items like "state.db is in WAL mode on a cross-VM filesystem (virtiofs/9p)" (which every host-mount deployment has). The toolkit mapped non-zero → `fail`, so `agx upgrade` rolled back a healthy v0.21.6 — and printed only "1 doctor check(s) failed" because the report was discarded before the revert replaced the container. Now: `_check_hermes_doctor` returns `warn` (with the flagged lines) when the output contains `Found N issue(s)`, `fail` only when doctor couldn't run; the upgrade's doctor phase calls `ops.doctor(raise_on_fail=False)` and names every failing check in its `HealthCheckFailure`. Same release switched GitHub/image tags from calver (`v2026.9.24`) to semver (`v0.21.6`): harmless for the toolkit because `outdated` compares tags by equality and `prune` orders images by Docker `CreatedAt` — keep it that way, never sort Hermes tags lexically or as versions.
- **ChatGPT-subscription Codex OAuth is ONE single-use refresh-token chain per login — never let two copies of it exist.** The retired "import bridge" (`<data-dir>/.codex` bind-mounted at `/home/hermes/.codex:ro`, seeded into Hermes' pool by `hermes setup`) did exactly that: the host file and the agent's pooled credential were two copies of one chain, so ANY refresh of the host copy (`agx codex refresh`, `codex auth status`, the CLI's own rotation) invalidated the agent's token ("Your authentication token has been invalidated", 2026-08-27) and vice versa. Rules: (1) provider auth is created in-container with `hermes auth add openai-codex --type oauth --no-browser` and owned by Hermes alone; (2) the toolkit never refreshes `<data-dir>/.codex` on the user's behalf (`agx codex refresh` retired); (3) after `hermes auth remove` of a bridge-seeded credential Hermes prints "Suppressed openai-codex device_code source — it will not be re-seeded", which is correct and wanted. Separately, upstream Hermes has an UNRESOLVED class where the chain dies every 1–3 weeks with the internal refresh stalling (#65346, closed not-planned) — there is no pre-warning possible (the access token is refreshed continuously), only prompt detection: `ops._check_hermes_credential_pool` reads `last_status` (`exhausted`/`dead`) + `last_error_reason` from `/opt/data/auth.json` (as root through the container, never printing token values) and `agx doctor-cron` mails on state change. Mitigation that keeps the agent answering is Hermes' `fallback_providers` (fires immediately on 401/403 — the startup-path gap #7230 is closed upstream but unverified by us).
- **Codex auth ≠ OpenAI API key.** Hermes' `openai-codex` provider knows how to drive the ChatGPT-subscription OAuth flow; nothing else does. Of the supported memory backends, only `holographic` works with Codex auth alone — it doesn't call out for embeddings or LLM. Don't introduce a "Codex proxy" path for the others; it would violate OpenAI ToS and break on every flow rotation.
- **Per-agent secrets live in `<data-dir>/<name>/.env`**, NOT the project-level `<data-dir>/.env`. The project file is for compose `${VAR}` interpolation only (HERMES_UID/GID, OLLAMA_API_KEY). The per-agent file is wired into each container via compose `env_file: ./<name>/.env` so its KEY=VALUE pairs become container env. Managed by `agx secret {set,unset,list,clear}` — values are never printed back, key names must match `^[A-Z][A-Z0-9_]*$`. Both fragments (Hermes and OpenClaw) include the env_file clause; the file is created (empty) by `agx create` so compose validation passes before any secrets are set.
- **Hermes filters env vars before spawning sandboxed subprocesses** (`terminal.env_passthrough` in `config.yaml`, defaults to `[]`). A secret in the container env is visible to Hermes' built-in Python tools (which read `os.environ` directly) but NOT to anything the `terminal` or `execute_code` tools spawn — meaning the LLM's own shell-based "is this configured?" diagnostics return false negatives. `agx secret set` therefore *also* adds the key to `terminal.env_passthrough` (Hermes agents only; OpenClaw doesn't have this concept). `agx secret unset` removes it. Idempotent on both sides. Per Hermes' docs: "For env vars not declared by any skill, add them to terminal.env_passthrough." Same wiring applies to `agx firecrawl up/down` for the FIRECRAWL_API_KEY/URL pair.
- **Host arch threads through `firecrawl_cmd.FLOATING_REFS` because Firecrawl's `api` image ships per-arch tags, not a multi-arch manifest.** `ghcr.io/firecrawl/firecrawl:linux-amd64` and `:linux-arm64` are separate single-arch images. `firecrawl_cmd._docker_arch()` reads `platform.machine()` (host == VM arch under Multipass — no cross-arch virt) and picks the right tag at module-import time. `nuq-postgres` has no arm64 tag at all — runs under qemu-user emulation on arm64 hosts; doctor's `arm64_emulation` check surfaces this. The other three (playwright/redis/rabbitmq) ship multi-arch manifests so a single tag suffices. See `docs/runbook.md#running-on-arm64--raspberry-pi-5` for the RPi5 deployment story.
- **Firecrawl self-host is project-scoped, not per-agent**, and pinned by digest. Upstream only publishes floating tags (`latest`, `linux-amd64`); the toolkit resolves each to a `@sha256:…` digest on first `agx firecrawl up` via `docker pull` + `docker image inspect`, writes the digests to `<data-dir>/.firecrawl-state.json`, and only ever references them by digest in compose. Subsequent `up` invocations reuse the captured digests; `agx firecrawl up --upgrade` re-resolves. Postgres data lives at `<data-dir>/firecrawl/postgres/` (bind mount, duplicity-friendly). `agx create` checks `firecrawl_cmd.is_installed(cfg)` after compose-up and auto-adds FIRECRAWL_API_KEY/URL to the new Hermes agent's `terminal.env_passthrough` — so a fresh agent created while firecrawl is up needs zero further wiring.
- **A VM-backend migration (multipass → libvirt, or any VM rebuild) silently strands the firecrawl stack.** The host data dir survives wholesale — compose service blocks, project `.env`, postgres bind-mount, and each agent's `env_passthrough` wiring all persist — but the five firecrawl containers live only in the *old* VM's Docker engine and never cross to the new VM, so `agx firecrawl status` shows them `absent` (not `exited`) and a wired agent's scrape calls fail connection-refused, silently. Two traps make this hard to spot: (1) `.firecrawl-state.json` (the digest-pin record) is *also* commonly lost in the migration, and `firecrawl_cmd.is_installed(cfg)` requires it — so the `is_installed`-gated checks (e.g. arm64 emulation) skip and nothing flags the gap; (2) a naive `agx firecrawl up` with the state file gone takes the no-state branch and **re-resolves digests against upstream floating tags = an unintended upgrade**. Correct recovery: reconstruct `.firecrawl-state.json` from the digests still pinned in compose (each `firecrawl-<role>` service's own `image` round-trips back to `images[role]` in `compose.firecrawl_service_fragments`), THEN `agx firecrawl up` reuses those exact pins. The `firecrawl_running` doctor check (`ops._check_firecrawl_running`) now surfaces the state: it gates on compose-presence (NOT `is_installed`, so it fires even with the state file gone) and warns only when ≥1 agent is still wired but the api container isn't running — a stack that's stopped *and* unwired is a deliberate `agx firecrawl down` and stays quiet.

| `agx fix-perms` | works | refused | `fixperms_cmd.fix_perms` raises on non-Hermes. The `/opt/data` permission drift + image-baked-path classes don't apply to OpenClaw (`/home/node/.openclaw`, no `usermod`/HERMES_UID dance) |
| `agx reseat` | works | works | Rewrites the agent's service fragment from the current template, preserving port(s)/tag/env_file/depends_on/extra-volume additions (diffed against the stock fragment; when in doubt, preserve). Hermes-only steps (cont-init hook materialization, /opt/data + install-path chown) skip for OpenClaw |
| Auto-chown of image-baked paths (`HERMES_WRITABLE_PATHS`) | runs after every recreate | not applicable | targets `/opt/hermes/scripts` + `/home/hermes` specifically |
| `agx codex skill-enable/disable` | works | refused by design | `codex.py` raises `if agent_type != "hermes"`. OpenClaw owns its Codex plugin — mounting toolkit-Codex on top would conflict |
| `agx ollama configure/status` | feeds Hermes config | not wired | OpenClaw reads its own provider config; toolkit's `[ollama]` block (EXTERNAL Ollama only) isn't propagated. Distinct from `[inference]` (in-VM local engines) — `[ollama]` keeps its localhost-refusal semantics |
| `agx inference {up,down,status,load,unload}` | works | works | Project-scoped Ollama + per-model llama-cpp services in the VM. Engines run as siblings (firecrawl pattern); shared models dir at `<data-dir>/models/`. Hermes agents reach them via Docker DNS (`http://ollama:11434/v1`). vLLM deliberately not supported — needs GPU passthrough which Multipass lacks (see GH #2 for libvirt investigation) |
| `agx model {pull,list,rm}` | works | works | Pulls into shared models dir. Ollama supports HF refs natively (`hf.co/<repo>:<quant>`); llama-cpp gets a separate HF download path via `huggingface_hub` |
| `agx model use <agent> --engine X --model Y` (`--profile`) | works | refused with explicit hint | Writes structured `model:` block to Hermes config.yaml. Engines: in-VM `ollama`/`llama-cpp` (Docker-DNS base_url) plus `external-ollama` ([ollama] block's URL — e.g. GPU inference on the host). `--context-length` writes model.context_length AND a per-model `custom_providers` entry matched by base_url (what `/model` switch + display consult); REQUIRED for external-ollama since the server's OLLAMA_CONTEXT_LENGTH cap can't be probed and /api/show over-reports the native window (silent-truncation trap). For OpenClaw, the rejection message includes the exact `base_url` to paste into `openclaw configure` since the toolkit stays out of OpenClaw's plugin lifecycle |
| LLM/provider credentials, vision provider, web-search provider | edited via toolkit (`hermes auth add ...` etc.) | **managed entirely inside OpenClaw** — `openclaw configure`, in-container UI, `models auth login` | the toolkit never writes OpenClaw credential files |

The rationale, restated: the toolkit's job is **infrastructure** (VM, compose, networking, host data, image pinning, upgrade safety) — not **agent-internal configuration**. For Hermes we leaned in because `hermes_config.py` could safely round-trip its YAML; OpenClaw's plugin manager owns mutation, so the toolkit stays at the env-and-mount boundary unless we add a comparable `openclaw_config.py` module with the same atomicity guarantees.

## Hermes terminology — don't conflate

Three distinct concepts that all sound related. Future doc work and any tooling we add must keep them separate:

| Term | What it is | Where it lives | CLI |
|---|---|---|---|
| **Profile** | A state-isolated Hermes instance — separate `$HERMES_HOME` with its own auth/sessions/skills/config/memories. State isolation only, NOT a security boundary | `$HERMES_HOME/profiles/<name>/` | `hermes profile {list,create --clone,use,delete,rename,export,import,install}` |
| **Personality** (SOUL.md + `/personality`) | The agent's persistent voice/identity (file) plus session-level overlays (preset or custom in `agent.personalities` in `config.yaml`) | `$HERMES_HOME/SOUL.md` | edit file directly; `hermes setup --section agent` |
| **Skill** | Folder of procedural knowledge in the open Agent-Skills format; loaded on demand | `$HERMES_HOME/skills/<id>/SKILL.md` | `hermes skills {browse,search,install,update,uninstall}` |

The toolkit's model is **one container per toolkit "agent"** = one `$HERMES_HOME`. The default recommendation is **one container + topical skills**, not one container per persona. Earn a second container only when LLM provider, connectivity, upgrade cadence, resource limits, or blast-radius isolation actually differ. See `docs/tutorial.md` §3 for the full decision tree.

**Hermes profile-gateway token rules (updated 2026-08 — the old "no native per-channel dispatcher" claim is obsolete).** Two *independent* profile gateways still cannot share a bot token (enforced — startup fails fast naming both profiles). BUT since ≥ v2026.8.x the *multiplexed* gateway mode supports `profile_routes` (gateway/profile_routing.py): ONE bot token serving multiple profiles, routed by guild/chat/thread id — a native gateway-side per-channel persona dispatcher. Channel-aware persona routing options are now: (a) one bot + topical skills, (b) one bot + interactive `/personality` overlay, (c) separate toolkit agents with separate bot users, or (d) one bot + multiplexed profile_routes (per-profile state/secrets isolation; note one unsafe security config in any profile aborts the whole multiplexer, and profiles remain a state boundary, not a security boundary — same-container profiles can read each other's HERMES_HOME incl. .env via the filesystem).

**Upstream vs toolkit posture on profiles (updated 2026-07 — don't cite the old "disposable sandboxes only" framing):** upstream now positions profiles as full production agents — per-profile gateways are dynamically registered s6-supervised services in the official image, and upstream's *default* Docker topology is one container hosting all profile gateways. A 2026-07-17 spike (v2026.7.7.2, libvirt/virtiofs) verified the mechanics work in our containers too: `hermes profile create` registers the s6 slot live AND pre-creates `/opt/data/logs/gateways/<profile>` as the hermes uid — the root-mkdir-on-shared-mount class does NOT fire for profile gateways — and the running set auto-resumes across restarts/recreates via per-profile `gateway_state.json`. Two standing caveats remain: (1) profiles are not a security boundary — upstream is explicit ("Profiles do not sandbox the agent") and tool subprocesses share the real `HOME` across profiles by default (`terminal.home_mode: profile` is the opt-in tightening); the container is our inner trust boundary. (2) Profiles share one installation — no per-profile version pinning/canary (profile *distributions* version profile content, not the Hermes runtime). The "pod" pattern (containers = trust domains; same-trust personas = profile gateways within one container) is now fully supported: tier-1 guardrails (2026-07: cont-init pre-creates every profile's gateway log dir on boot; doctor's `_check_profile_gateways` watches desired-vs-actual s6 state) AND the tier-2 management surface (2026-08, GH #6): `hermes_config` threads a `profile` dimension (`normalize_profile`/`profile_home`; the `0.0.0.0` dashboard refusal applies to every profile write, and doctor's `_check_profile_dashboard_bindings` sweeps all profile configs for hand-edited non-loopback binds), `agx secret {set,unset,clear} --profile` (env_passthrough per profile; the `.env`→container-env half is container-wide by nature), `agx conversations {status,export} --profile` (per-profile `state.db`), `agx model use --profile`, `agx memory enable/disable --profile` (holographic/mem0 place their stores INSIDE the profile home — never share a memory DB across profiles; openviking refuses per-profile, its sibling service is agent-scoped), and `agx profile list <agent>` (read-only enumeration: config/state presence + gateway desired/s6 state; Hermes owns create/delete via `hermes profile`). The dashboard item from the original tier-2 list is OBSOLETE upstream: one `HERMES_DASHBOARD=1` instance (port 9119) multiplexes all co-located profiles via per-request profile routing — no per-profile ports needed. Posture: profiles for same-trust personas (incl. gateway-exposed ones, each with its own bot token or via multiplexed `profile_routes`); differing risk/sensitivity still gets its own container. Full decision tree + user-facing caveats: `docs/tutorial.md` §3 + §6.

**Messaging-platform connectivity** is via `hermes gateway` (long-running messaging gateway in-container) plus platform-specific subcommands: `hermes slack` (manifest generator), `hermes whatsapp` (pairing). Mattermost / Matrix / Discord / Teams / IRC / Rocket.Chat are **not** built-in as of Hermes v1.x — users go via community skills (`hermes skills search <platform>`) or a custom gateway adapter. The toolkit's `0.0.0.0` refusal applies to dashboards specifically; if a connector strictly needs an inbound webhook port, document users to add it via `docker-compose.override.yml` (and prefer outbound modes like Slack Socket Mode where possible).

```
src/agx_cli/

  config.py       # pydantic v2 schema + tomlkit round-trip of ~/.config/agx/config.toml
  ui.py           # human/JSON output, confirmation prompts, --yes bypass
  errors.py       # exit-code mapping (0 success, 1 user error, 2 runtime, 3 health)
  mp.py           # VM-backend DISPATCHER (was multipass primitives). Thin wrappers over `cfg.vm.backend`'s module. Re-exports value types (MpResult, BootstrapStatus, parse_bootstrap_ok) for backward compat.
  backends/       # VM-backend implementations
    __init__.py   # VmBackend Protocol, MpResult/BootstrapStatus, parse_bootstrap_ok, get_backend_module
    multipass.py  # Multipass impl (cross-platform default; was mp.py before the abstraction)
    libvirt.py    # libvirt/KVM impl, Linux-only, EXPERIMENTAL. Cloud-init seed ISO + virt-install + ssh/scp. GPU passthrough auto-detect (NVIDIA/AMD/Intel) + IOMMU validation + hostdev XML attach. configure(data_dir) MUST be called before any primitive — cli.main does this when libvirt is active.
    bare_metal.py # No-VM impl, Linux-only (see GH #5). exec_in_vm/transfer collapse to subprocess + shutil on the host, with DOCKER_HOST pinned to the rootless socket (configure(socket_path), called by cli.main); mount/launch/start_vm/stop_vm/snapshot are no-ops or explicit refusals. verify_bootstrap() probes rootless-Docker prereqs and emits BOOTSTRAP_OK (verify-only — surfaces apt/curl/systemctl hints rather than installing). open_shell() spawns a subshell with CWD=data-dir + DOCKER_HOST set for `vm shell`. Compose project-dir = host data-dir (vm.init sets vm_agents_root=host_data_dir for this backend).
  compose_runner.py  # docker compose verbs via multipass exec
  compose.py      # ruamel round-trip, Hermes/OpenClaw service fragments, port allocator. Also owns the managed s6 cont-init.d perms hook: `ensure_cont_init_script` materializes `<data-dir>/.toolkit/cont-init/99-fixperms` (body in templates.HERMES_CONT_INIT_FIXPERMS), bind-mounted read-only into every Hermes container so install-path chown + gateway-logdir pre-create run on EVERY boot. Materialized (Hermes only) by create/reseat/fix-perms/upgrade before their `compose up`; persists on the project dir thereafter. Detects+repairs a Docker-auto-created directory at the bind source.
  hermes_config.py   # round-trip edit of each agent's config.yaml; refuses 0.0.0.0; optimistic-concurrency check (read_doc hash vs file right before write_atomically's rename). Profile-aware (GH #6 tier 2): normalize_profile/profile_home + a `profile` param on config_path/read_doc/write_atomically target `.data/profiles/<p>/config.yaml`; validation execs with HERMES_HOME pointed at the profile home
  journal.py      # generic phase journal (create/remove/rename/upgrade)
  vm.py           # init/start/stop/shell/status/snapshot/restore/destroy
  agents_cmd.py   # create/list/remove/rename; prepare_openclaw_state (OpenClaw state dirs → uid 1000 before every create/reseat start)
  ops.py          # start/stop/restart/logs/exec/setup/doctor
  upgrades.py     # state machine: host-data-snapshot → vm-snapshot → pull → recreate → doctor → rollback; auto-prunes old upgrade artifacts after success (see prune_cmd)
  prune_cmd.py    # `agx prune [name] [--keep N] [--dry-run]` — generation-counted retention of upgrade artifacts (host tarballs in .upgrades/, pre-upgrade VM snapshots, superseded agent image tags). Also `auto_prune_after_upgrade`, called by upgrades.upgrade INSIDE its flock (do not re-acquire). Image pruning is repo-scoped and only ever touches hermes/openclaw repos; compose-referenced tags + defaults.*_image_tag baseline are always protected.
  export_cmd.py   # export/import/export-cron (host-cron, idempotent)
  codex.py        # login/status/skill-enable/skill-disable — the sandbox SKILL only (never provider auth); `refresh` is a retired hidden stub
  doctor_cron.py  # `agx doctor-cron {install,uninstall,status,run}` — host cron: ops.doctor(raise_on_fail=False) every N min, diff the failing set against <data-dir>/.doctor-cron/state.json, mail on CHANGE only via host `sendmail -t` (no SMTP config in the toolkit; install refuses without a sendmail binary)
  ollama_cmd.py   # configure/status/clear — points the toolkit at an external Ollama / OpenAI-compatible endpoint (the toolkit does NOT run Ollama)
  secrets_cmd.py  # per-agent .env management (API keys for skills like firecrawl); never the project .env
  mounts_cmd.py   # `agx mount {add,remove,list}` — give an agent access to specific host folders. Per-agent isolation (no cross-agent sharing); manifest at `<data-dir>/<agent>/.mounts.json`; VM-side path `<vm-host-extras>/<agent>/<sha256[:8]>-<basename>` (deterministic per container path; on bare_metal the bind source is the host folder — `MountEntry.volume_source`); writes runtime volumes to `docker-compose.override.yml` (NEVER the main compose) + sandbox volumes to Hermes `terminal.docker_volumes`. `--target sandbox` Hermes-only. Read-only default; `--rw` prompts. Rolls back the VM mount if compose/config writes fail. Also auto-applies bidirectional ACLs on the host folder (agent's subuid gets read/write access; on `--rw`, host user gets default ACL for files the agent writes back). No sudo (user owns the folder).
  permissions.py  # POSIX-ACL helpers for `agx mount add` ONLY (host folders the user owns — never agent data dirs, where ACLs can't hold). `compute_container_subuid(host_uid, container_uid=1000)` does the rootless-Docker subuid math (cached). `apply_acl_argv` / `remove_acl_argv` emit setfacl argvs without executing; `run_owned` runs them as the user. `run_with_sudo` is the toolkit's one printed-and-confirmed HOST sudo runner (`access mount/unmount`, bare-metal data-dir delete) — shlex-joined display, `yes=True` skips the confirm. `probe_acl_support(path)` gates grants. CRITICAL: `setfacl -d -m` rejects the `d:` prefix on the spec — the helpers emit the bare `u:<uid>:rwx` form for default ACLs.
  access_cmd.py   # `agx access {mount,unmount,list}` — idmapped bind-mount VIEW of an agent's subuid-owned state dir (Hermes `<agent>/.data`; OpenClaw `<agent>/.openclaw`, host-owned `workspace` skipped) at `<view-root>/<agent>`. One confirmed `sudo mount` (verified afterwards via mountinfo; multi-target rollback; refuses symlinked/non-empty/foreign mountpoints and view-root↔data-dir nesting). State file `.access-views.json`; `refuse_if_view_registered` is the lifecycle guard called by remove/rename/migrate-data; `view_rows` feeds doctor's `host_view` check. `legacy_acl_dirs` surfaces leftover default ACLs from the retired grant mechanism. Refuses on `--data-dir-in-vm`; supported on bare-metal.
  idmap_view.py   # PURE helpers for access_cmd: `idmap_spec` (swap + identity ranges from the on-disk owner), `mount_options` (ro|rw + nosuid,nodev,noexec,nosymfollow), `fstab_line` (octal-escaped, `nofail`), `/proc/self/mountinfo` parser, `expected_root` (root field is relative to the containing filesystem — separate /home!), `view_status` → mounted|not-mounted|stale|foreign.
  edit_cmd.py     # `agx edit <agent> <path>` — container-routed edit of a Hermes text file in $EDITOR (realpath-confined, base64 fetch, config.yaml forced through hermes_config.write_atomically, optimistic re-read under the flock). Never touches the host-side data path.
  profile_cmd.py  # `agx profile list <agent>` — read-only enumeration of Hermes profiles (config/state presence, gateway desired + s6 state). The toolkit never creates/deletes profiles; Hermes owns that. s6-svstat is called by absolute /command path (exec PATH lacks /command — same pitfall as the cont-init hook).
  fixperms_cmd.py # `agx fix-perms <agent>` — force-recreates container, chowns /opt/data, chmods 755 for the recurring permission-drift bug
  firecrawl_cmd.py # project-level self-hosted Firecrawl (api + playwright + redis + rabbitmq + postgres). `agx firecrawl up` self-pins images to digests on first run, auto-wires every Hermes agent's terminal.env_passthrough.
  tailscale_cmd.py # `agx tailscale {up,down,status,upgrade}` — tailnet access to the VM. NOT a sibling container (rootless Docker can't own /dev/net/tun): tailscaled runs as a VM-OS systemd service via apt + mp.exec primitives. `up` without --auth-key emits the browser login URL (payload key auth_url) and exits 0; state file `.tailscale-state.json` gates the doctor check (opt-in, like firecrawl). Refuses on bare_metal (the toolkit never mutates the HOST OS). `status`/`up` list non-loopback ports from docker-compose.override.yml as tailnet-reachable URLs.
  conversations_cmd.py # `agx conversations {status,export}` — read-only stats from the Hermes session store (default or per-profile state.db via --profile) + Markdown transcript export for migration. Active = within agent.gateway_auto_continue_freshness; per-platform breakdown; top-N active table. No mutations, no flock.
  outdated_cmd.py # `agx outdated [<name>]` — fetches latest GitHub Releases tag per agent type, classifies each agent as current/outdated/unknown. Owns the ONLY GitHub release lookup (`fetch_latest_tag`, used by `vm init`, `create`, `upgrade`) and the release-tag → image-tag conversion (`image_tag_from_release` / `normalize_image_tag`).
  inference_cmd.py # `agx inference {up,down,status,load,unload}` — project-scoped Ollama + per-model llama.cpp services. Pull-and-digest-pin on first up (firecrawl pattern). ## Backups
```

The user runs **duplicity on the host** as the only backup layer. The toolkit does NOT implement an internal backup engine. Don't add restic, borg, or off-site replication. `agx export` produces a clean archive in `<data-dir>/backups/` — duplicity picks it up.

## Testing

`pytest` (unit, no network), `mypy --strict`, `ruff check + ruff format --check`. The integration smoke suite is opt-in via `pytest -m multipass`. Never in CI.

Unit tests never reach GitHub: an autouse fixture in `tests/conftest.py` makes `outdated_cmd._fetch_json` return `None` (stub `fetch_latest_tag` / `_fetch_json` per test to simulate upstream) — `create` now resolves the latest release, and an un-stubbed test silently pinned whatever upstream shipped that day.

The unit suite covers: compose round-trip and golden files, port allocator with override files, mp argv quoting, BOOTSTRAP_OK parser failure modes, upgrade state machine with injected runner, codex skill-enable / skill-disable, Hermes config round-trip, journal resume, flock serialization, sandbox-image-tag slugification, memory plugin enable/disable round-trip per plugin (holographic, mem0, openviking), Ollama URL schema validation (localhost refusal).

The integration smoke suite lives at `tests/integration/` (marker `multipass`; a `libvirt` marker is registered for backend-specific tests — currently none, prefer backend-agnostic). It is deselected by default via `addopts = -m 'not multipass'`, so bare `pytest` and `pytest tests/unit` never run it; run it with `pytest -m multipass tests/integration/`. It drives the installed `agx` console script as a subprocess against the REAL default config (`~/.config/agx/config.toml`) — never `multipass`/`virsh` directly, so it works on any backend — parsing `--json` stdout and asserting exit codes. Prerequisites: an already-healthy deployment; the session gate runs `agx --json doctor` and SKIPS everything when the console script or config is missing, the VM is down, or doctor is red. First run pulls the pinned Hermes image (the session fixture runs `agx create`), so budget minutes. Safety guarantees: read-only against pre-existing agents (no `vm init/destroy/rebuild`, no upgrades, no writes to their data); everything it creates carries the reserved `itest-` prefix (one disposable Hermes agent per session plus scratch dirs under `<data-dir>/.itest/`) and is torn down in fixture finalizers even on assertion failure. What it proves end-to-end: doctor green + JSON shape, create/list/exec exit-code propagation, per-agent secrets reaching container env (and `terminal.env_passthrough` cleanup on unset), `agx mount` volumes actually delivered by Docker (the `docker-compose.override.yml` regression class — unit tests assert the file's content; only this proves Docker READS it), export→import content round-trip via an in-container sentinel (same-name by design: `agx import` extracts the archive's embedded top-level dir), non-empty `agx logs`, and the one-JSON-document-per-command stdout contract.

## Conventions

- Pinned image tags — no `:latest` outside an explicit canary path.
- Every destructive op behind `--yes`.
- Every command emits machine-readable output under `--json`.
- Exit codes are load-bearing: 0 / 1 / 2 / 3.
- No `print()` — everything goes through `ui.py` so `--json` works.
- Subprocess invocations use list-form argv (never `shell=True`).
- New cross-layer mistakes get added to the "Critical cross-layer pitfalls" section above.
