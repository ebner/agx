# Project context for Claude Code

## What this is

`agents` is a host-side Python CLI that manages AI agents (Hermes Agent from Nous Research, OpenClaw) inside a single Multipass VM with rootless Docker. The host invokes only `multipass` — it never talks to the in-VM Docker daemon directly. Outer trust boundary = VM. Inner trust boundary = one Docker container per agent. The defense-in-depth motivation is the 2026 wave of agent-marketplace malware and skill-execution CVEs.

## Locked architecture rules (do not relitigate)

0. **VM backend is pluggable.** `cfg.vm.backend` selects `multipass` (cross-platform default), `libvirt` (Linux-only, experimental — enables GPU passthrough; see GH #2), or `bare_metal` (Linux-only, no VM at all — see GH #5). `mp.py` is a dispatcher; the real implementations live in `agents_cli/backends/{multipass,libvirt,bare_metal}.py`. Backend modules are duck-typed (free functions matching `VmBackend` Protocol). `cli.main` calls `mp.set_backend(get_backend_module(cfg.vm.backend))` once at startup; everything else uses `mp.foo(...)` and stays backend-agnostic. **Never add new VM-host primitives directly to `mp.py`** — add them to ALL THREE backend modules + the dispatcher in `mp.py`.
1. **Rootless Docker inside the VM.** Daemon runs as `ubuntu`, socket at `<docker_socket_path>` (read from `[vm_runtime]` in config — set by BOOTSTRAP_OK). Never hardcode the path or the UID.
2. **One mount, one source of truth.** Host `<data-dir>` is mounted at VM `/home/ubuntu/agents` with explicit `multipass mount -u <host-uid>:1000 -g <host-gid>:1000`. All per-agent data, the compose file, the `.env`, exports, and the toolkit-scoped Codex auth live under this path. The VM disk only holds OS + Docker engine + image cache. Opt-out is `vm init --data-dir-in-vm` — **recommended for SQLite-heavy workloads** (Hermes' kanban/sessions/insights stores use WAL, which doesn't work over the 9p share; in-VM ext4 fixes that). Under `--data-dir-in-vm` agent state is host-visible only via `agents export` archives; `agents export-cron install --time 02:30,08:30,14:30,20:30` gives you 6-hourly archives that duplicity picks up natively.
3. **Toolkit-scoped Codex auth** at `<data-dir>/.codex/` — NEVER the user's personal `~/.codex/`. `agents codex login` sets `CODEX_HOME=<data-dir>/.codex`.
4. **The CLI owns the compose file.** Users get `docker-compose.override.yml` for hand edits. Never heredoc through `multipass exec` — always: flock → ruamel.yaml round-trip → write host temp via `compose.host_staging_dir(cfg)` (= `<host_data_dir>/.staging/`) → `multipass transfer` to `<vm_agents_root>/.compose.<pid>.<uuid>.new` → `docker compose --project-directory <vm_agents_root> -f ... --env-file <vm_agents_root>/.env config -q` validation → VM-side `mv` to `docker-compose.yml` (atomic same-fs rename) → cleanup. Host staging path is NOT under `/tmp/` (snap-confined `multipass` — the default Ubuntu install — cannot SFTP from `/tmp`: `cannot access`) and NOT under `$HOME/.cache/` (snap's home interface excludes dotfile paths: `Permission denied`). Staging under the host data dir works because that dir is already `multipass mount`ed into the VM, so multipass has explicit access — guaranteed on both snap and deb installs. Every module that `multipass transfer`s a host file into the VM (`compose`, `hermes_config`, `codex` for Dockerfile + auth-tar sync) uses `compose.host_staging_dir(cfg)` — do NOT introduce new `/tmp` or `~/.cache` paths. `compose.cleanup_stale_temps(cfg)` is invoked by `vm.start` and at the head of every mutation. Same pattern applies to per-agent `config.yaml` writes via `hermes_config.write_atomically`, which validates via `hermes config validate` exec'd inside the running container (best-effort — silently skipped if the container isn't up yet).
5. **Image-source allowlist** is a parsed `(registry, repo)` tuple match — `nousresearch/hermes-agent`, `openclaw/openclaw`, `volcengine/openviking` (memory sidecar), `ghcr.io/firecrawl/firecrawl` + `ghcr.io/firecrawl/playwright-service` + `ghcr.io/firecrawl/nuq-postgres` (firecrawl stack), and `redis` + `rabbitmq` (firecrawl dependencies). Reject `hermes-agent.org` and any registry-prefixed variant. `validate_image_ref` handles `repo`, `repo:tag`, AND `repo@sha256:…` (digest pin) forms — strips `@sha256:…` BEFORE partitioning on `:`. New sibling-service backends require explicit allowlist additions in `compose.py`.
6. **Dashboard binding** is `127.0.0.1`/`localhost` only. The CLI refuses any Hermes config change to `0.0.0.0`.
7. **Every mutation holds `<data-dir>/.agents.lock`** (`flock`). Read-only commands skip the lock. Two parallel `agents create` calls must serialize.
8. **Every multi-phase op writes a phase journal** at `<data-dir>/.journal/<op>-<name>-<utc>.json`. Re-running the command resumes from the last completed phase. `doctor` flags journals older than 24 h.
9. **Compose service blocks are written once and never auto-regenerated.** When the service-fragment template evolves (new env var, changed volume layout), existing agents keep their stale block forever. `agents reseat <name>` is the explicit "rewrite this agent's compose service entry from the current fragment, preserving port + image tag + env_file additions + depends_on additions, then force-recreate" command. Run after toolkit upgrades.
10. **`docker-compose.override.yml` is sacred** — the toolkit appends to it (currently only via `agents mount`) but never rewrites it from a template, never deletes user keys, never runs it through reseat. Both layers — `docker-compose.yml` (toolkit-owned, full rewrites allowed) and `docker-compose.override.yml` (additive only) — exist precisely so user-and-`agents mount` additions survive every `agents reseat` / `agents upgrade`. New features that need to add per-agent runtime knobs (e.g. extra volumes, extra env, extra ports) go in the override file via `compose.read_override_doc` / `compose.write_override_atomically`, not the primary compose. Mutations must hold `<data-dir>/.agents.lock` like every other compose write.

## Critical cross-layer pitfalls (already fixed; don't reintroduce)

- **Snap-Multipass + libvirt on the same host fight over `/dev/kvm` group ownership.** `/etc/udev/rules.d/70-snap.multipass.rules` tags `/dev/kvm` with `snap_multipass_multipassd`, which causes `snap-device-helper` to reassign the device's group to snapd's sandboxed namespace (typically `systemd-resolve`). libvirt-qemu (group `kvm`) then can't open `/dev/kvm` and every libvirt VM start fails with "Could not access KVM kernel module: Permission denied". Fix is to drop `/etc/udev/rules.d/99-fix-kvm-group.rules` with a `RUN+=` that re-asserts `chgrp kvm /dev/kvm` AFTER snap's rule (99- sorts after 70-). Documented in `docs/runbook.md#using-the-libvirt-backend`.
- **libvirt + virtiofs requires `<memoryBacking><source type='memfd'/><access mode='shared'/></memoryBacking>` in the domain XML.** Without it, `virsh attach-device` of a `<filesystem type='virtiofs'>` block succeeds but the guest mount hits "Transport endpoint is not connected". The toolkit emits `--memorybacking source.type=memfd,access.mode=shared` on every `virt-install`; never hand-edit the launch path to drop it.
- **libvirt + virtiofs cannot snapshot a running VM** — vhost-user backend lacks `VHOST_USER_PROTOCOL_F_LOG_SHMFD`. `vm.take_snapshot` / `vm.restore_snapshot` detect the case (backend=libvirt AND not data-dir-in-vm) and run a confirmed stop → snapshot → start cycle. Why not detach-virtiofs-snapshot-reattach: live `umount` is refused while Docker containers have bind mounts underneath; `umount -l` works but leaves containers with stale FDs (SQLite-WAL corruption risk for state.db / kanban.db). Full-VM-stop matches container lifecycle and is what `agents vm stop` already does cleanly.
- **libvirt VM init must be transactional** — `virt-install` can leave a defined-but-unstartable domain if e.g. `wait_for_ssh` times out after the domain is registered. `vm.init`'s libvirt branch wraps launch + wait + GPU-attach in try/except and calls `libvirt._cleanup_partial_domain` on failure (destroy + snapshot-delete --metadata + undefine --remove-all-storage). Without this, retry would be blocked by the orphan domain.
- **AMD systems often ship with `amd_iommu=off` in the kernel cmdline** (Strix Halo / Ryzen AI MAX, several Ryzen laptops). It's a leftover BIOS-stability workaround from early 2025. GPU passthrough is impossible until the user updates BIOS + flips to `amd_iommu=on iommu=pt`. The toolkit doesn't try to detect or fix this (host-level + reboot); doctor checks just surface `iommu_group=""` for affected GPUs.
- **Rootless-Docker subuid mapping is why agent files look "foreign" on the host.** Container uid 1000 (the hermes/openclaw runtime user) maps to host uid `<subuid_base> + 999` (typically 100999) under rootless Docker. The agent's data dir is owned by 100999 with mode 700; the host user (uid 1000) can't `ls` it without sudo. The toolkit solves this two ways: (1) `agents create` calls `access_cmd.auto_grant_on_create` to set a *default ACL* on the fresh data dir before the container starts, so every file the container later writes inherits `u:<host-uid>:rwx`; (2) `agents access grant <name>` is the explicit fix for agents that pre-date this hook (or for re-applying drift). `agents mount add` auto-applies the symmetric ACL (host folder → agent's subuid). All callers go through `permissions.py` — never compute subuid math, run setfacl, or assume a uid mapping in feature code. **Don't** try to "fix" subuid ownership by chown'ing inside the container — the entrypoint reverses it on the next start. ACLs are the right tool because they layer additional grants without changing ownership; they survive chowns, container recreates, and the rootless engine's own subuid logic.
- **ACLs survive chowns — but chmod clobbers the ACL *mask*.** The Hermes entrypoint chmods subuid-owned paths (`.data` → 700, auth files → 600), which resets each object's POSIX-ACL mask to `---`: the host-user entry `auto_grant_on_create` installed stays present but reads `#effective:---`, so the host user can't traverse or delete the tree. Bit us live 2026-07: `agents remove` died with `PermissionError: '.data'`, and the re-run then hit "not found in compose" because the interrupted run had already scrubbed the compose entry — stranding the journal. Two fixes, both load-bearing: (1) `permissions.apply_acl_argv` always includes `m::rwx` in the spec (setfacl does NOT reliably recompute an existing `---` mask despite what the manpage implies), and `agents_cmd._delete_data_dir` self-heals on PermissionError by re-applying the host-user ACL via `run_with_sudo` (printed + confirmed; `--yes` skips) before retrying; (2) `remove` consults `Journal.find_resumable` before raising "not found in compose", recovering `agent_type` from journal meta (recorded at begin; pre-meta journals fall back safely — a missing compose entry proves the container phases completed). Any new host-side traversal of agent data dirs (exports, doctor probes, future features) must expect the masked-ACL state and either go through the self-heal pattern or degrade with a `sudo` hint.
- **`--backend bare_metal` forfeits the VM trust boundary** — the host becomes the boundary. A compromised agent that escapes its container reaches the host directly. The defense-in-depth motivation in this file still applies for most users; bare-metal is opt-in for single-user dev workstations / dedicated LLM boxes only. The init flow warns the user explicitly. Three concrete behavior differences from VM-mode that are easy to miss: (a) bootstrap is **verify-only** — `bare_metal.verify_bootstrap` probes rootless-Docker prerequisites and refuses with hints (`sudo apt install ...`, `curl ... | sh`, `loginctl enable-linger`) rather than running sudo on the user's behalf; (b) `vm.init` sets `cfg.paths.vm_agents_root = cfg.paths.host_data_dir` so `compose_runner._base_argv` produces correct host paths unchanged — any new code that interpolates `vm_agents_root` for an SSH/multipass-exec context must NOT assume it differs from `host_data_dir`; (c) snapshots are refused (no VM disk to snapshot — use `agents export` + host-level duplicity/restic). When adding a new feature, gate VM-specific code paths on `cfg.vm.backend in ("multipass", "libvirt")` rather than enumerating bare-metal exclusions, so future backends don't silently break.
- **`terminal.docker_volumes` paths are interpreted by the VM Docker daemon**, not by paths inside the Hermes container. Sandbox volume entries use VM-side host paths like `/home/ubuntu/agents/.codex:/<sandbox-user>/.codex:ro`.
- **Hermes runtime container needs `DOCKER_HOST` env** plus the rootless socket mount, otherwise its CLI can't reach the daemon to spawn the sandbox.
- **Multipass snapshots do NOT cover the host-mounted data-dir.** Upgrade flow takes BOTH a VM snapshot AND a host-data tarball (in `<data-dir>/.upgrades/`).
- **Rootless Docker ships NO container-log rotation** — the json-file driver grows unbounded, and one chatty container can take the VM disk down alone (firecrawl-postgres: 2.8 GB in 5 days; a transient disk-full at 2026-08-24 00:30 ENOSPC'd rabbitmq mid-write, wedging it in `health: starting` and killing web search for every wired agent, since a stopped `firecrawl-api` also drops its Docker-DNS name → agents see "could not resolve host", not a connection error). The bootstrap now writes `~/.config/docker/daemon.json` with `log-opts: max-size=50m, max-file=3` BEFORE the daemon's first start (step 3b2; never clobbers an existing file). Caveat: log-opts apply per-container at CREATE time — containers created before the option keep unbounded logs until their next recreate (reseat/upgrade/firecrawl `up --upgrade`).
- **Upgrade artifacts used to accumulate unboundedly and filled the VM disk to 100% (2026-08 outage).** Each `agents upgrade` leaves a superseded image tag (~4-9 GB for Hermes) in the VM's Docker cache plus a VM snapshot and a host tarball; eight releases of routine upgrades exhausted a 58 GB VM disk, and the symptom was obscure — Hermes' gateway answered "session storage could not be written" because the container's overlay fs (VM root disk) had 0 bytes free while `/opt/data` (host mount) had plenty. Two guards now exist and must both survive refactors: doctor's `vm_disk` check (`df -Pk /` in the VM — the host-side `disk_space` check can't see the VM disk) and the post-upgrade auto-prune (`prune_cmd.auto_prune_after_upgrade`, keeping `[upgrades].keep_generations` generations). Retention is generation-counted, NOT age-based: `agents rollback` only uses the newest generation, and age-based expiry could delete the only rollback point of a rarely-upgraded agent.
- **Multipass mount does not always survive stop/start.** `agents vm start` verifies and remounts, then runs a write/read/unlink probe.
- **Multipass mount MUST be `--type native`, not the default `classic` / fuse.sshfs.** Rootless Docker cannot bind-mount paths from a fuse.sshfs filesystem into a container — kernel returns `operation not supported` and every agent fails on first start. Native uses 9p (Linux/QEMU) or virtiofs (macOS/HyperKit), which Docker handles fine. Native mounts require the VM stopped to add, so `vm._ensure_mount` does a stop→mount→start dance when needed; mounts persist across reboots so it's a one-time cost.
- **No `user:` override on Hermes container under rootless Docker.** Container UID 0 maps to the rootless host user (`ubuntu`/1000) which owns the multipass-mounted data dir. Setting `user: 1000:1000` would push the process into the rootless subuid range (e.g. host uid 100999) and every write into `/opt/data` would be permission-denied. The compose fragment pins HOME via env instead so the Codex import-bridge path is stable regardless of image USER/HOME drift.
- **Compose env must pin `PATH=/opt/hermes/.venv/bin:...`** — the Hermes image's entrypoint prepends this internally, but `docker exec` (used by `agents doctor` to run `hermes doctor`) bypasses the entrypoint and would otherwise hit `executable file not found`.
- **Rootless Docker install does NOT ship the compose plugin.** `get.docker.com/rootless` installs only daemon + CLI. The bootstrap adds Docker Inc's apt source and installs `docker-compose-plugin` system-wide (lands at `/usr/libexec/docker/cli-plugins/`, picked up by the rootless CLI via plugin auto-discovery).
- **`/home/ubuntu/bin` MUST be on the system PATH** (`/etc/environment`). The rootless install puts `docker` there; `multipass exec` doesn't source `.profile` so without this the toolkit hits `bash: docker: command not found`. The bootstrap prepends it idempotently.
- **OpenClaw service paths are per-agent** (`./<name>/.openclaw`, `./<name>/workspace`) so multiple named OpenClaw agents don't collide.
- **Codex sandbox image tag** must be slugified (`agents/hermes-sandbox-codex:<sha256(base)[:12]>`) — base refs contain `/` and `:`.
- **Image-baked Hermes paths need runtime-user write — they're lost on every container recreate.** Symptom: `hermes setup` (or any other in-container install) hits `EACCES: permission denied, mkdir '/opt/hermes/scripts/whatsapp-bridge/node_modules'`. Cause: `/opt/hermes/scripts/` and `/home/hermes/` are baked into the image owned by root (or whatever USER the image was built as). The runtime user is `hermes`/1000 after the entrypoint's `usermod`, but `usermod` doesn't migrate the home dir, and image-baked subdirs of `/opt/hermes` stay root-owned. Every recreate (`docker rm -f` + `compose up`) wipes the container's overlay fs, so any chown is ephemeral. Remediation: `fixperms_cmd.chown_hermes_install_paths(cfg, svc, huid)` runs after every recreate — called from `agents create` (service_up phase), `agents fix-perms`, and `agents reseat`. Targets list lives at `fixperms_cmd.HERMES_WRITABLE_PATHS`; each entry pairs a target with a tuple of paths to `-prune` so the recursive chown doesn't follow read-only bind-mounts (notably the Codex import bridge at `/home/hermes/.codex:ro`). **Any new code path that force-recreates a Hermes container must call this helper after start** or `hermes setup`'s install branches will silently regress. **Durable fix (2026-06):** the toolkit now bind-mounts a managed s6 cont-init.d script (`templates.HERMES_CONT_INIT_FIXPERMS`, materialized by `compose.ensure_cont_init_script` into `<data-dir>/.toolkit/cont-init/99-fixperms`) at `/etc/cont-init.d/99-toolkit-fixperms` in every Hermes container. It re-applies this chown on EVERY boot — restart, upgrade-recreate, host-reboot — not just toolkit-driven recreates, which is what kept re-breaking after `agents upgrade`. New agents get the mount at create; existing agents pick it up via `agents reseat`. The materializer (`ensure_cont_init_script`) runs at create (before the fragment is written), reseat, fix-perms, AND upgrade, before each issues its `compose up`; the file then persists on the project dir so other recreate paths (`secret set`, `memory`, `codex skill-*`, vm rebuild) find it present, and a template bump is re-applied on the next reseat. The explicit `chown_hermes_install_paths` call ALSO runs in `upgrade`'s recreate now (it historically didn't — the root of the treadmill), so even an agent whose fragment predates the hook (not yet reseated) is fixed on upgrade; it stays belt-and-suspenders for reseated agents and the first boot before the mount exists. NOTE: this fixes the *permission* half only — the WhatsApp bridge's `node_modules` still lives on the overlay fs and is wiped on every recreate, and its `@whiskeysockets/baileys` **git** dependency sometimes reinstalls empty (`ERR_MODULE_NOT_FOUND`); the fix there is a clean `npm ci` in `/opt/hermes/scripts/whatsapp-bridge`, a separate concern from perms.
- **`/opt/data` permission drift is a recurring class of bug.** Symptom: `agents exec coder hermes <anything>` hits `PermissionError: '/opt/data/.env'` (or similar). Cause: the Hermes image entrypoint *should* `usermod -u $HERMES_UID hermes` on container start, but sometimes doesn't — `docker compose up -d` skips entrypoint when it thinks there's no drift, and stale containers from before HERMES_UID was wired in keep running with hermes=10000. `/opt/data` ends up owned by uid 10000 mode 700; `agents exec` runs at uid 1000; EACCES. Detection: `_check_hermes_data_dir_accessible` in `ops.py` probes `stat /opt/data` as the runtime uid every doctor run. Remediation: `agents fix-perms <agent>` — force-remove the container, recreate fresh (entrypoint runs), then `chown -R <huid>:<huid> /opt/data` + `chmod 755 /opt/data`. The chmod 755 is a band-aid for when the entrypoint *still* doesn't honour HERMES_UID; mode-600 files (auth.json etc.) stay private.
- **The s6 supervision tree runs as container-root, but `/opt/data` is a 9p/virtiofs mount that IGNORES the container's root capabilities — only the runtime `hermes` uid can write there.** This is the non-obvious asymmetry behind a class of "agent silently stops replying" bugs. As container-root, `chown`/`mkdir` on the **overlay fs** (e.g. `/opt/hermes/scripts`) WORKS (CAP_CHOWN honored in the userns); the SAME op on the **9p-backed `/opt/data`** FAILS with `Permission denied`, because container-uid-0 maps to the unprivileged host/VM user while the mount is owned by the hermes subuid, and 9p enforces DAC at the VM level where the container's userns caps don't apply. It first bit us on Hermes ≥ v2026.5.29: the image's `gateway-default/log/run` does `mkdir -p /opt/data/logs/gateways/default` **as root**, which fails under rootless Docker, so the gateway log service hot-loops, `hermes gateway` never sustains, and the agent receives/answers nothing (`agents logs <name>` shows `s6-log: fatal: unable to mkdir ...`). The cont-init hook encodes the split-privilege rule: chown the overlay install-paths AS ROOT, but pre-create `/opt/data/logs/gateways/default` via `s6-setuidgid hermes` (called by absolute path `/command/s6-setuidgid`, since the cont-init PATH doesn't include `/command`). The leaf must be pre-created (not just the parent) and owned by hermes so the image's buggy root-`mkdir -p` no-ops and `s6-log` (which runs as hermes) can write. Upstream bug — worth reporting to Nous; worked around toolkit-side meanwhile.
- **`localhost` / `127.0.0.1` / `0.0.0.0` are refused in `[ollama]` URLs** (`OllamaConfig._validate_url`). Inside the VM those resolve to the VM itself, not to the host where the user is actually running Ollama. The toolkit suggests the multipass NAT gateway (`multipass info <vm>` → IPv4) when surfacing the error.
- **Memory backends needing embeddings/LLM read from `[ollama]` only.** The toolkit does NOT manage an Ollama instance. mem0 and OpenViking refuse to install when `[ollama]` is empty (mem0 falls back to `OPENAI_API_KEY` in `.env` if present; OpenViking does not, since its fact-extraction loop would melt a personal ChatGPT subscription).
- **Codex auth ≠ OpenAI API key.** Hermes' `openai-codex` provider knows how to drive the ChatGPT-subscription OAuth flow; nothing else does. Of the supported memory backends, only `holographic` works with Codex auth alone — it doesn't call out for embeddings or LLM. Don't introduce a "Codex proxy" path for the others; it would violate OpenAI ToS and break on every flow rotation.
- **Per-agent secrets live in `<data-dir>/<name>/.env`**, NOT the project-level `<data-dir>/.env`. The project file is for compose `${VAR}` interpolation only (HERMES_UID/GID, OLLAMA_API_KEY). The per-agent file is wired into each container via compose `env_file: ./<name>/.env` so its KEY=VALUE pairs become container env. Managed by `agents secret {set,unset,list,clear}` — values are never printed back, key names must match `^[A-Z][A-Z0-9_]*$`. Both fragments (Hermes and OpenClaw) include the env_file clause; the file is created (empty) by `agents create` so compose validation passes before any secrets are set.
- **Hermes filters env vars before spawning sandboxed subprocesses** (`terminal.env_passthrough` in `config.yaml`, defaults to `[]`). A secret in the container env is visible to Hermes' built-in Python tools (which read `os.environ` directly) but NOT to anything the `terminal` or `execute_code` tools spawn — meaning the LLM's own shell-based "is this configured?" diagnostics return false negatives. `agents secret set` therefore *also* adds the key to `terminal.env_passthrough` (Hermes agents only; OpenClaw doesn't have this concept). `agents secret unset` removes it. Idempotent on both sides. Per Hermes' docs: "For env vars not declared by any skill, add them to terminal.env_passthrough." Same wiring applies to `agents firecrawl up/down` for the FIRECRAWL_API_KEY/URL pair.
- **Host arch threads through `firecrawl_cmd.FLOATING_REFS` because Firecrawl's `api` image ships per-arch tags, not a multi-arch manifest.** `ghcr.io/firecrawl/firecrawl:linux-amd64` and `:linux-arm64` are separate single-arch images. `firecrawl_cmd._docker_arch()` reads `platform.machine()` (host == VM arch under Multipass — no cross-arch virt) and picks the right tag at module-import time. `nuq-postgres` has no arm64 tag at all — runs under qemu-user emulation on arm64 hosts; doctor's `arm64_emulation` check surfaces this. The other three (playwright/redis/rabbitmq) ship multi-arch manifests so a single tag suffices. See `docs/runbook.md#running-on-arm64--raspberry-pi-5` for the RPi5 deployment story.
- **Firecrawl self-host is project-scoped, not per-agent**, and pinned by digest. Upstream only publishes floating tags (`latest`, `linux-amd64`); the toolkit resolves each to a `@sha256:…` digest on first `agents firecrawl up` via `docker pull` + `docker image inspect`, writes the digests to `<data-dir>/.firecrawl-state.json`, and only ever references them by digest in compose. Subsequent `up` invocations reuse the captured digests; `agents firecrawl up --upgrade` re-resolves. Postgres data lives at `<data-dir>/firecrawl/postgres/` (bind mount, duplicity-friendly). `agents create` checks `firecrawl_cmd.is_installed(cfg)` after compose-up and auto-adds FIRECRAWL_API_KEY/URL to the new Hermes agent's `terminal.env_passthrough` — so a fresh agent created while firecrawl is up needs zero further wiring.
- **A VM-backend migration (multipass → libvirt, or any VM rebuild) silently strands the firecrawl stack.** The host data dir survives wholesale — compose service blocks, project `.env`, postgres bind-mount, and each agent's `env_passthrough` wiring all persist — but the five firecrawl containers live only in the *old* VM's Docker engine and never cross to the new VM, so `agents firecrawl status` shows them `absent` (not `exited`) and a wired agent's scrape calls fail connection-refused, silently. Two traps make this hard to spot: (1) `.firecrawl-state.json` (the digest-pin record) is *also* commonly lost in the migration, and `firecrawl_cmd.is_installed(cfg)` requires it — so the `is_installed`-gated checks (e.g. arm64 emulation) skip and nothing flags the gap; (2) a naive `agents firecrawl up` with the state file gone takes the no-state branch and **re-resolves digests against upstream floating tags = an unintended upgrade**. Correct recovery: reconstruct `.firecrawl-state.json` from the digests still pinned in compose (each `firecrawl-<role>` service's own `image` round-trips back to `images[role]` in `compose.firecrawl_service_fragments`), THEN `agents firecrawl up` reuses those exact pins. The `firecrawl_running` doctor check (`ops._check_firecrawl_running`) now surfaces the state: it gates on compose-presence (NOT `is_installed`, so it fires even with the state file gone) and warns only when ≥1 agent is still wired but the api container isn't running — a stack that's stopped *and* unwired is a deliberate `agents firecrawl down` and stays quiet.

## Codex paths — how Hermes and OpenClaw differ

| Agent | Codex as LLM | Codex as tool |
|---|---|---|
| Hermes | `model.provider: openai-codex`. Mounted Codex auth at `/home/hermes/.codex:ro` is an import bridge; once `hermes setup` runs, persistent auth lives at `/opt/data/.hermes/auth.json` on the bind-mounted data dir. The compose fragment pins BOTH the runtime user (`user: ${HERMES_UID}:${HERMES_GID}`) AND HOME (`HOME=/home/hermes` in env), so the import target is a function of compose settings — NOT of the image's USER/HOME, which have drifted between Hermes releases (newer images run as `root` with no explicit HOME). `agents create` only ensures the image is pulled; it no longer refuses on USER/HOME drift. | Opt in via `agents codex skill-enable`. CLI builds a derived sandbox image with Codex CLI baked in and `ENV CODEX_HOME=/codex`; volume entry mounts the toolkit Codex auth at `/codex:ro`. User-independent — works for sandbox images running as root, pn, node, etc. The whole operation holds `<data-dir>/.agents.lock`. |
| OpenClaw | OpenClaw bundles its own Codex plugin. Run `openclaw models auth login --provider openai-codex` inside the container. **Never** mount Codex into OpenClaw — would conflict. | Same plugin path. |

## Toolkit feature coverage — Hermes vs OpenClaw

Most of the toolkit's day-2 ergonomics are Hermes-shaped. OpenClaw owns more of its own configuration surface (credentials, memory, plugin lifecycle) by design, so the toolkit deliberately stays out of those layers — touching them would race or conflict with OpenClaw's plugin manager. The matrix below is the canonical map; **anything not listed as "works" must explicitly gate on `agent_type == "hermes"` or do a no-op for OpenClaw**.

| Feature | Hermes | OpenClaw | Notes |
|---|---|---|---|
| VM lifecycle, `create`/`list`/`remove`/`rename`/`start`/`stop`/`restart`/`logs`/`exec` | works | works | universal CRUD + lifecycle |
| `agents setup <name>` | runs `hermes setup` | runs `openclaw onboard` | dispatched in `ops.py` / `agents_cmd.py` (`binary = "hermes" if agent_type == "hermes" else "openclaw"`) |
| `agents upgrade` / `rollback` / `pull` | works | works | type-agnostic state machine; image base differs (`HERMES_IMAGE_BASE` vs `OPENCLAW_IMAGE_BASE`) |
| `agents export` / `import` / `export-cron` | works | works | `tar` path for both |
| `agents doctor` | full surface | partial | VM checks universal; per-agent Hermes probes (`hermes doctor`, `/opt/data` access, Codex mount, `fixperms` traversal) skip for OpenClaw |
| `agents secret {set,unset,list,clear}` | full | env-only | per-agent `.env` written for both (compose `env_file:`); **`terminal.env_passthrough` editing is Hermes-only** — OpenClaw has no equivalent sandbox env filter, its shell tools inherit container env directly |
| `agents firecrawl up/down/status` | up runs stack, auto-wires Hermes agents via `terminal.env_passthrough` + compose env interpolation | up runs stack, auto-wires OpenClaw agents via compose env interpolation only | OpenClaw's bundled Firecrawl plugin reads `FIRECRAWL_API_KEY` + `FIRECRAWL_BASE_URL` (note: `BASE_URL`, not Hermes' `API_URL`); the OpenClaw compose fragment bridges the asymmetry by mapping `FIRECRAWL_BASE_URL=${FIRECRAWL_API_URL:-}` so both ultimately resolve to the same project `.env` entry. **Important second step the toolkit does NOT take**: OpenClaw's plugin still needs `plugins.entries.firecrawl.enabled: true` flipped via `openclaw configure` (or picked during onboarding) — the toolkit stays out of OpenClaw's plugin lifecycle. Stale fragments of either type (created before the firecrawl env entries landed) are remediated with `agents reseat <name>` — `firecrawl up` surfaces that hint |
| `agents tailscale up/down/status/upgrade` | works | works | Project-scoped, agent-type-agnostic: puts the VM on the user's tailnet (tailscaled as VM-OS systemd service — see tailscale_cmd.py). Primary use: reaching the Hermes dashboard (`HERMES_DASHBOARD=1` env via `agents secret set` + port 9119 published in the override file) from other tailnet devices without SSH tunnels. Refused on bare_metal |
| `agents memory enable/disable` (holographic / mem0 / openviking) | works | refused | `memory/__init__._require_hermes` raises. OpenClaw has its own memory architecture |
| `agents conversations status <name>` | works | refused (early, before container exec) | Reads Hermes' `/opt/data/state.db` (sessions + messages tables) for active-context stats. Reports counts within `agent.gateway_auto_continue_freshness` window plus per-platform breakdown. OpenClaw uses a different session schema, so the check rejects before touching the container — same posture as `memory` and `fix-perms` |
| `agents conversations export <name> --to <dir>` | works | refused (early) | Writes one Markdown transcript per session under the target dir. Primary use case is migration (see `docs/migration.md`); idempotent so safe under cron for archival |
| `agents outdated [<name>]` | works | works | Type-agnostic. Reads each agent's pinned compose tag, fetches latest from GitHub Releases (`/releases/latest` upstream-filters pre-releases; `--include-prerelease` opts into `/releases?per_page=10`). Surfaces `current` / `outdated` / `unknown` (network fetch failed). firecrawl-* services are skipped (digest-pinned, not tag-pinned) |
| `agents upgrade <name> --latest` | works | works | Resolves upstream tag and pins it, AND refreshes `defaults.<type>_image_tag` in `config.toml` so future `agents create` starts on the latest baseline. Refuses (not silently no-ops) when GitHub is unreachable — would otherwise be a successful-looking no-op |
| `agents prune` | works | works | Type-agnostic. Deletes upgrade artifacts older than the newest N generations (default `[upgrades].keep_generations = 2`): `.upgrades/` tarballs + `pre-upgrade-*` VM snapshots per agent, superseded image tags per agent repo. Runs automatically after every successful `agents upgrade` (best-effort, never fails the upgrade); `keep_generations = 0` disables the automatic pass. Never touches user-named snapshots, other repos (firecrawl/ollama/openviking), or `agents export` backups (those have their own `[export_cron].keep_last`) |
| `agents fix-perms` | works | refused | `fixperms_cmd.fix_perms` raises on non-Hermes. The `/opt/data` permission drift + image-baked-path classes don't apply to OpenClaw (`/home/node/.openclaw`, no `usermod`/HERMES_UID dance) |
| `agents reseat` | works | works | Rewrites the agent's service fragment from the current template, preserving port(s)/tag/env_file/depends_on/extra-volume additions (diffed against the stock fragment; when in doubt, preserve). Hermes-only steps (cont-init hook materialization, /opt/data + install-path chown) skip for OpenClaw |
| Auto-chown of image-baked paths (`HERMES_WRITABLE_PATHS`) | runs after every recreate | not applicable | targets `/opt/hermes/scripts` + `/home/hermes` specifically |
| `agents codex skill-enable/disable` | works | refused by design | `codex.py` raises `if agent_type != "hermes"`. OpenClaw owns its Codex plugin — mounting toolkit-Codex on top would conflict |
| `agents ollama configure/status` | feeds Hermes config | not wired | OpenClaw reads its own provider config; toolkit's `[ollama]` block (EXTERNAL Ollama only) isn't propagated. Distinct from `[inference]` (in-VM local engines) — `[ollama]` keeps its localhost-refusal semantics |
| `agents inference {up,down,status,load,unload}` | works | works | Project-scoped Ollama + per-model llama-cpp services in the VM. Engines run as siblings (firecrawl pattern); shared models dir at `<data-dir>/models/`. Hermes agents reach them via Docker DNS (`http://ollama:11434/v1`). vLLM deliberately not supported — needs GPU passthrough which Multipass lacks (see GH #2 for libvirt investigation) |
| `agents model {pull,list,rm}` | works | works | Pulls into shared models dir. Ollama supports HF refs natively (`hf.co/<repo>:<quant>`); llama-cpp gets a separate HF download path via `huggingface_hub` |
| `agents model use <agent> --engine X --model Y` | works | refused with explicit hint | Writes structured `model:` block to Hermes config.yaml. For OpenClaw, the rejection message includes the exact `base_url` to paste into `openclaw configure` since the toolkit stays out of OpenClaw's plugin lifecycle |
| LLM/provider credentials, vision provider, web-search provider | edited via toolkit (`hermes auth add ...` etc.) | **managed entirely inside OpenClaw** — `openclaw configure`, in-container UI, `models auth login` | the toolkit never writes OpenClaw credential files |

The rationale, restated: the toolkit's job is **infrastructure** (VM, compose, networking, host data, image pinning, upgrade safety) — not **agent-internal configuration**. For Hermes we leaned in because `hermes_config.py` could safely round-trip its YAML; OpenClaw's plugin manager owns mutation, so the toolkit stays at the env-and-mount boundary unless we add a comparable `openclaw_config.py` module with the same atomicity guarantees.

## Hermes terminology — don't conflate

Three distinct concepts that all sound related. Future doc work and any tooling we add must keep them separate:

| Term | What it is | Where it lives | CLI |
|---|---|---|---|
| **Profile** | A state-isolated Hermes instance — separate `$HERMES_HOME` with its own auth/sessions/skills/config/memories. State isolation only, NOT a security boundary | `$HERMES_HOME/profiles/<name>/` | `hermes profile {list,create --clone,use,delete,rename,export,import,install}` |
| **Personality** (SOUL.md + `/personality`) | The agent's persistent voice/identity (file) plus session-level overlays (preset or custom in `agent.personalities` in `config.yaml`) | `$HERMES_HOME/SOUL.md` | edit file directly; `hermes setup --section agent` |
| **Skill** | Folder of procedural knowledge in the open Agent-Skills format; loaded on demand | `$HERMES_HOME/skills/<id>/SKILL.md` | `hermes skills {browse,search,install,update,uninstall}` |

The toolkit's model is **one container per toolkit "agent"** = one `$HERMES_HOME`. The default recommendation is **one container + topical skills**, not one container per persona. Earn a second container only when LLM provider, connectivity, upgrade cadence, resource limits, or blast-radius isolation actually differ. See `docs/tutorial.md` §3 for the full decision tree.

**Hermes profiles are NOT a way to multiplex one chat-bot across personas.** Each profile that runs a gateway binds its own bot token; two profiles cannot share a bot (enforced — second gateway is blocked with an error naming the conflict), and there is no native gateway-side per-channel dispatcher. Channel-aware persona routing = (a) one bot + topical skills, (b) one bot + interactive `/personality` overlay, or (c) separate toolkit agents with separate bot users.

**Upstream vs toolkit posture on profiles (updated 2026-07 — don't cite the old "disposable sandboxes only" framing):** upstream now positions profiles as full production agents — per-profile gateways are dynamically registered s6-supervised services in the official image, and upstream's *default* Docker topology is one container hosting all profile gateways. A 2026-07-17 spike (v2026.7.7.2, libvirt/virtiofs) verified the mechanics work in our containers too: `hermes profile create` registers the s6 slot live AND pre-creates `/opt/data/logs/gateways/<profile>` as the hermes uid — the root-mkdir-on-shared-mount class does NOT fire for profile gateways — and the running set auto-resumes across restarts/recreates via per-profile `gateway_state.json`. The toolkit still does NOT manage that mode, for three standing reasons: (1) profiles are not a security boundary — upstream is explicit ("Profiles do not sandbox the agent") and tool subprocesses share the real `HOME` across profiles by default (`terminal.home_mode: profile` is the opt-in tightening); the container is our inner trust boundary. (2) The toolkit's day-2 surface (secrets/`env_passthrough`, `model use`, `conversations`, `memory`, doctor's Hermes probes, the `0.0.0.0` refusal) reads/writes the DEFAULT profile's `config.yaml`/`state.db` only. (3) Profiles share one installation — no per-profile version pinning/canary. The "pod" pattern (containers = trust domains; same-trust personas = profile gateways within one container) has tier-1 guardrails landed (2026-07): the cont-init hook globs `/opt/data/profiles/*/` and pre-creates each profile's gateway log dir on every boot (restored/imported data dirs arrive without it), and doctor's `_check_profile_gateways` warns when a profile's `gateway_state.json` wants `running` but its s6 service is down or its log service is flapping. Tier 2 (profile-aware config/secrets/conversations/dashboard surface) remains open in GH #6. Recommended posture meanwhile: profiles for interactive use (scratch personas, A/B personality tests, state-contained experiments, profile distributions); gateway-exposed personas get containers. Full decision tree + user-facing caveats: `docs/tutorial.md` §3 + §6.

**Messaging-platform connectivity** is via `hermes gateway` (long-running messaging gateway in-container) plus platform-specific subcommands: `hermes slack` (manifest generator), `hermes whatsapp` (pairing). Mattermost / Matrix / Discord / Teams / IRC / Rocket.Chat are **not** built-in as of Hermes v1.x — users go via community skills (`hermes skills search <platform>`) or a custom gateway adapter. The toolkit's `0.0.0.0` refusal applies to dashboards specifically; if a connector strictly needs an inbound webhook port, document users to add it via `docker-compose.override.yml` (and prefer outbound modes like Slack Socket Mode where possible).

    libvirt.py    # libvirt/KVM impl, Linux-only, EXPERIMENTAL. Cloud-init seed ISO + virt-install + ssh/scp. GPU passthrough auto-detect (NVIDIA/AMD/Intel) + IOMMU validation + hostdev XML attach. configure(data_dir) MUST be called before any primitive — cli.main does this when libvirt is active.
    bare_metal.py # No-VM impl, Linux-only (see GH #5). exec_in_vm/transfer collapse to subprocess + shutil on the host; mount/launch/start_vm/stop_vm/snapshot are no-ops or explicit refusals. verify_bootstrap() probes rootless-Docker prereqs and emits BOOTSTRAP_OK (verify-only — surfaces apt/curl/systemctl hints rather than installing). open_shell() spawns a subshell with CWD=data-dir + DOCKER_HOST set for `vm shell`.   compose.py      # ruamel round-trip, Hermes/OpenClaw service fragments, port allocator. Also owns the managed s6 cont-init.d perms hook: `ensure_cont_init_script` materializes `<data-dir>/.toolkit/cont-init/99-fixperms` (body in templates.HERMES_CONT_INIT_FIXPERMS), bind-mounted read-only into every Hermes container so install-path chown + gateway-logdir pre-create run on EVERY boot. Materialized (Hermes only) by create/reseat/fix-perms/upgrade before their `compose up`; persists on the project dir thereafter. Detects+repairs a Docker-auto-created directory at the bind source.
  hermes_config.py   # round-trip edit of each agent's config.yaml; refuses 0.0.0.0
  journal.py      # generic phase journal (create/remove/rename/upgrade)
  vm.py           # init/start/stop/shell/status/snapshot/restore/destroy
  agents_cmd.py   # create/list/remove/rename
  ops.py          # start/stop/restart/logs/exec/setup/doctor
  upgrades.py     # state machine: host-data-snapshot → vm-snapshot → pull → recreate → doctor → rollback; auto-prunes old upgrade artifacts after success (see prune_cmd)
  prune_cmd.py    # `agents prune [name] [--keep N] [--dry-run]` — generation-counted retention of upgrade artifacts (host tarballs in .upgrades/, pre-upgrade VM snapshots, superseded agent image tags). Also `auto_prune_after_upgrade`, called by upgrades.upgrade INSIDE its flock (do not re-acquire). Image pruning is repo-scoped and only ever touches hermes/openclaw repos; compose-referenced tags + defaults.*_image_tag baseline are always protected.
  export_cmd.py   # export/import/export-cron (host-cron, idempotent)
  codex.py        # login/refresh/status/skill-enable/skill-disable
  ollama_cmd.py   # configure/status/clear — points the toolkit at an external Ollama / OpenAI-compatible endpoint (the toolkit does NOT run Ollama)
  secrets_cmd.py  # per-agent .env management (API keys for skills like firecrawl); never the project .env
  mounts_cmd.py   # `agents mount {add,remove,list}` — give an agent access to specific host folders. Per-agent isolation (no cross-agent sharing); manifest at `<data-dir>/<agent>/.mounts.json`; VM-side path `<vm-host-extras>/<agent>/<sha256[:8]>-<basename>` (deterministic per container path); writes runtime volumes to `docker-compose.override.yml` (NEVER the main compose) + sandbox volumes to Hermes `terminal.docker_volumes`. `--target sandbox` Hermes-only. Read-only default; `--rw` prompts. Rolls back the VM mount if compose/config writes fail. Also auto-applies bidirectional ACLs on the host folder (agent's subuid gets read/write access; on `--rw`, host user gets default ACL for files the agent writes back). No sudo (user owns the folder).
  permissions.py  # POSIX-ACL helpers. `compute_container_subuid(host_uid, container_uid=1000)` does the rootless-Docker subuid math (container uid N → host subuid_base + N - 1; cached). `apply_acl_argv` / `remove_acl_argv` emit setfacl argvs without executing — callers pick `run_owned` (user-owned paths, no sudo) or `run_with_sudo` (subuid-owned paths, prints + confirms unless `yes=True`). `probe_acl_support(path)` is the gate for "this fs carries ACLs" before any grant. `assess_host_access(path, uid)` is the doctor's drift signal: ok|missing|path-missing. CRITICAL: `setfacl -d -m` rejects the `d:` prefix on the spec — the helpers emit the bare `u:<uid>:rwx` form for default ACLs. Used by mounts_cmd (auto-ACL on host folders) + access_cmd (explicit ACL on agent data dirs).
  access_cmd.py   # `agents access {grant,revoke,list}` — host user ↔ agent's subuid-owned data dir. Hermes targets `<agent>/.data`; OpenClaw targets BOTH `<agent>/.openclaw` and `<agent>/workspace`. Requires sudo (path owned by subuid 100999); prints exact setfacl argv and confirms unless `--yes`. Refuses on `--data-dir-in-vm`. No-op on bare-metal (container uid maps 1:1 to host user). `auto_grant_on_create` is the hook agents_cmd.create calls AFTER mkdir but BEFORE container start: sets default ACL granting host user rwx so files the container later creates inherit access — no sudo needed at that moment because the user owns the empty dir.
  fixperms_cmd.py # `agents fix-perms <agent>` — force-recreates container, chowns /opt/data, chmods 755 for the recurring permission-drift bug
  firecrawl_cmd.py # project-level self-hosted Firecrawl (api + playwright + redis + rabbitmq + postgres). `agents firecrawl up` self-pins images to digests on first run, auto-wires every Hermes agent's terminal.env_passthrough.
  tailscale_cmd.py # `agents tailscale {up,down,status,upgrade}` — tailnet access to the VM. NOT a sibling container (rootless Docker can't own /dev/net/tun): tailscaled runs as a VM-OS systemd service via apt + mp.exec primitives. `up` without --auth-key emits the browser login URL (payload key auth_url) and exits 0; state file `.tailscale-state.json` gates the doctor check (opt-in, like firecrawl). Refuses on bare_metal (the toolkit never mutates the HOST OS). `status`/`up` list non-loopback ports from docker-compose.override.yml as tailnet-reachable URLs.
  conversations_cmd.py # `agents conversations {status,export}` — read-only stats from /opt/data/state.db (Hermes session store) + Markdown transcript export for migration. Active = within agent.gateway_auto_continue_freshness; per-platform breakdown; top-N active table. No mutations, no flock.
  outdated_cmd.py # `agents outdated [<name>]` — fetches latest GitHub Releases tag per agent type, classifies each agent as current/outdated/unknown. `fetch_latest_tag` is also called by `upgrades.upgrade(to_latest=True)` (`--latest` flag) which bumps an agent to upstream AND refreshes the toolkit-wide default tag.
  inference_cmd.py # `agents inference {up,down,status,load,unload}` — project-scoped Ollama + per-model llama.cpp services. Pull-and-digest-pin on first up (firecrawl pattern). Distinct from `[ollama]` block which is for EXTERNAL Ollama; in-VM uses `[inference]`. vLLM intentionally not supported — see GitHub issue #2 (GPU passthrough requires libvirt).
  models_cmd.py  # `agents model {pull,list,rm,use}` — model lifecycle (Ollama Hub + HuggingFace via Ollama's hf.co/... refs; HF GGUF download for llama.cpp). `model use <agent> --engine X --model Y [--aux compression|vision|all]` writes the structured `model:` block (provider=custom + base_url + api_key) to the Hermes agent's config.yaml.

  templates.py    # bootstrap script body, sandbox Dockerfile, fallback image tags
scripts/vm-bootstrap.sh   # idempotent rootless Docker + Node-less / Codex-less setup; emits BOOTSTRAP_OK line

## Backups

The user runs **duplicity on the host** as the only backup layer. The toolkit does NOT implement an internal backup engine. Don't add restic, borg, or off-site replication. `agents export` produces a clean archive in `<data-dir>/backups/` — duplicity picks it up.

## Testing

`pytest` (unit, no network), `mypy --strict`, `ruff check + ruff format --check`. The integration smoke suite is opt-in via `pytest -m multipass`. Never in CI.

The unit suite covers: compose round-trip and golden files, port allocator with override files, mp argv quoting, BOOTSTRAP_OK parser failure modes, upgrade state machine with injected runner, codex skill-enable / skill-disable, Hermes config round-trip, journal resume, flock serialization, sandbox-image-tag slugification, memory plugin enable/disable round-trip per plugin (holographic, mem0, openviking), Ollama URL schema validation (localhost refusal).

The integration smoke suite lives at `tests/integration/` (marker `multipass`; a `libvirt` marker is registered for backend-specific tests — currently none, prefer backend-agnostic). It is deselected by default via `addopts = -m 'not multipass'`, so bare `pytest` and `pytest tests/unit` never run it; run it with `pytest -m multipass tests/integration/`. It drives the installed `agents` console script as a subprocess against the REAL default config (`~/.config/agents/config.toml`) — never `multipass`/`virsh` directly, so it works on any backend — parsing `--json` stdout and asserting exit codes. Prerequisites: an already-healthy deployment; the session gate runs `agents --json doctor` and SKIPS everything when the console script or config is missing, the VM is down, or doctor is red. First run pulls the pinned Hermes image (the session fixture runs `agents create`), so budget minutes. Safety guarantees: read-only against pre-existing agents (no `vm init/destroy/rebuild`, no upgrades, no writes to their data); everything it creates carries the reserved `itest-` prefix (one disposable Hermes agent per session plus scratch dirs under `<data-dir>/.itest/`) and is torn down in fixture finalizers even on assertion failure. What it proves end-to-end: doctor green + JSON shape, create/list/exec exit-code propagation, per-agent secrets reaching container env (and `terminal.env_passthrough` cleanup on unset), `agents mount` volumes actually delivered by Docker (the `docker-compose.override.yml` regression class — unit tests assert the file's content; only this proves Docker READS it), export→import content round-trip via an in-container sentinel (same-name by design: `agents import` extracts the archive's embedded top-level dir), non-empty `agents logs`, and the one-JSON-document-per-command stdout contract.

## Conventions

- Pinned image tags — no `:latest` outside an explicit canary path.
- Every destructive op behind `--yes`.
- Every command emits machine-readable output under `--json`.
- Exit codes are load-bearing: 0 / 1 / 2 / 3.
- No `print()` — everything goes through `ui.py` so `--json` works.
- Subprocess invocations use list-form argv (never `shell=True`).
- New cross-layer mistakes get added to the "Critical cross-layer pitfalls" section above.
